# Orchestrate a program

Core rules, kept at the top because a compaction re-injects only the start of this skill:
1. You route and judge; investigation, implementation, verification and browser work go one layer down (a worker, a card, a background subagent). You write no PR yourself.
2. A PR lands only through `orch land` once its required checks are green and its Codex review leaves nothing to act on (`references/landing.md`).
3. Exactly one background inbox wait runs at all times (`orch wait <slug>`, or without a program the peek wait in Step 5); after a compaction or restart, check it is alive before anything else.
4. Your turn ends on a short answer to the human; completion reaches you as a notification, never by polling.

You own the program, not the code. You frame it, write briefs, drain the inbox, keep dependencies and the land order honest, and decide. Orca already owns the mechanics: Run, Task and its deps, Dispatch, `check --wait`/ack, `ask`/`reply`, gates, the worker contract, recovery and release. This skill adds only the program layer.

**REQUIRED BACKGROUND:** at the start of every coordinator session, run `orca skills get orchestration` and read it. Every Orca command here comes from it; never compose one from memory.

Two modes share these rules. **Top-level:** the one session above every task session and program coordinator the human runs; read `references/top-level.md`. **Program:** one project driven to done through workers; the Steps below.

A session's mode is declared, never guessed from its terminal. Start it with `claude --agent agent-skills:orchestrator --name orchestrator` for the top-level, or `claude --agent agent-skills:lead --name lead:<slug>` for a program's coordinator or lead. A session already running, or a lead card whose launcher cannot pass flags, declares with a prompt line of its own: `ROLE: orchestrator` or `ROLE: lead <slug>`; `ROLE: none` silences either. The plugin's reorient hook reads the role from the session itself, so it survives compaction, resume and fork, and puts one reminder line before every prompt of a declared session. A lead card's first prompt carries its `ROLE` line (`references/brief.md` "Lead").

## Stay answerable

The human must get an answer from you within seconds, at any time. You route; you do not do the work.

- Inside your turn, only three things happen: routing a request to its owner, checks that finish in seconds (`orch status`, one `orca … --json` read, one `gh … --json` read), and answering the human.
- Investigation, implementation, verification, reviews, long waits and monitoring go to an Orca worker or a background subagent (`run_in_background`; implementation goes to a card, below) the moment the request arrives. Hand over the facts you already have; do not "take a quick look first".
- Never block in the foreground: no `until` loops, no `sleep`, no `check --wait` or `orch wait` without `run_in_background`, no back-to-back polling reads. The one background inbox wait you keep is in Step 5, "One inbox wait, always". A PR waiting on a human is read at most hourly, and a rate-limit error waits for its reset (`references/brief.md` LAND).
- Completion reaches you as a notification: the background task's completion, or the `orch wait` that wakes on worker_done, escalation or question. Between notifications, your turn is over.
- A request that would take you more than one short tool call is a delegation, even when you know the answer's shape.
- You write no PR: not code, not a doc, not a script, however small the follow-up. It goes to a card (a `worker-start` worker inside a program, otherwise a `/goal` card: `dispatch-card` §2, with an APPROVED line when the unit needs approved acts) or to Codex (`codex:rescue`), not to a background subagent, and you judge, review and land it. Under auto mode a background subagent's Edit or Write can get no verdict from the classifier; a unit already given to one restarts as such a card at the first failure, not after retries ("Refused acts"). The acts in `references/top-level.md`, "Acts only the human's session may take", are the only task work you do yourself, and none of them is writing a PR.
- These rules bind every layer above a worker: the top-level, a program coordinator, and a lead card (a coordinator another session started for one project, `references/brief.md` "Lead"). Such a layer judges results, lands, records decisions and puts what waits on the human in front of them. Investigation, implementation, verification, browser steps and new cards go one layer down. When a project has a lead, the layer above sends that project's work to the lead, never to the lead's workers and never into its own hands.
- A research answer that later tickets will build on (a contract, an authorization or security rule, a scope cut) is one model's draft until it is challenged. Before you post it as the ticket's answer, copy it into briefs or close the ticket, have a background subagent run `interrogate` on it, and fold the findings to act on into the answer: every brief that quotes it inherits its blind spots.
- A card that is stuck is not yours to finish: no merge, dispatch or browser step done in its place. A missing approval gets a new `/goal` card that carries it; a missing permission rule gets the human one `!` line ("Refused acts").
- What you started, you close, in the wake that tells you its work is over: a `worker_done`, or any message from a card that says it is done, whatever its form. Judge closing in that turn, before the merge or review the same wake brings: no later wake brings the report back. A background subagent or task you no longer need → `TaskStop` (never the one `orch wait`). A scratchpad or `.claude/worktrees/agent-*` worktree whose work landed or was dropped → `git worktree remove` (clean ones only). A card you made with `orca worktree create` or `dispatch-card` has no `worker_done`, so no `CLOSE OUT` line names it: once its PRs merge, check it. Its brief's `CLOSE` line should have closed it; if not, and `end-session` §4's Remove row holds in it and its idle screen says nothing is left, remove it (`orca worktree rm --worktree path:<card>`). A standing loop (a heartbeat routine, `/loop`) also reads the `done-card` items of `<state>/janitor-plan.json` (`reap-resources`) on every wake and closes each card of yours listed there the same way.

## When not to use

- One agent could finish inside the budget → do it in this session, or give it to one card with `handoff-ticket`. A program costs a coordinator.
- A single ticket handed to another session → `handoff-ticket`.

## Where each fact lives

| Fact | Owner |
|---|---|
| Goal | Orca Run `objective` (`run-create`), shown as the dashboard headline |
| Standing orders, predicate, merge policy, decisions, human digest | Program note in the notes store (`use-notes`), template `references/program-note.md` |
| Tickets, their state, which are derived | The tracker, through `use-tracker` (`tracker.py`) |
| PRs, CI, merges, stacks | GitHub, read there directly (a tracker's PR panel is a cache and lags) |
| Runs, tasks and their deps (the dependency graph), workers, questions, gates | Orca |
| Verdicts, lanes, land order, landings, main red/green, the concurrency cap, deps found after dispatch | `~/.claude/programs/<slug>/ledger.jsonl`, written only through `orch` |
| Briefs as sent | `~/.claude/programs/<slug>/briefs/<ticket>.md` |
| Decision trail | `~/.claude/programs/<slug>/decisions.tsv` (`show-me-your-work`) |
| Lessons: raw signals / what became of them | `signal` rows in the ledger / the lessons ledger in the notes store (`reflect`) |
| What the human watches | `orch-dash` dashboard (`references/dashboard.md`) |
| Who does what beside the ticket workers | Standing roles: main guardian, QA lead, flow improver, resource steward (`references/roles.md`) |

`orch` runs `scripts/prog.py` and `orch-dash` runs `scripts/dash.py`; the plugin's `bin/` puts both on the Bash PATH. Run either with no arguments for usage.

## Steps

1. **Frame.**
   - Read every ticket in scope.
   - Write the predicate as countable ticket IDs plus a final check on the real artifact ("A-246, 247, 117 Done and `verify-<app>` drives the quickstart on main"). Derive it yourself. If the tickets have no countable end, write your best predicate, mark it proposed in the digest, and go on. The predicate is the program's exit condition (principle **Work to an Exit Condition**): write its out-of-scope list beside it in the program note, and report progress as "N/M predicate items done", never as tickets filed.
   - Copy the human's goal into the standing orders verbatim, one sentence per order. A sentence that would have a worker write outside its worktree stays verbatim in the coordinator's list, and the workers' list gets its worker form: "put it in the worker_done body; the coordinator writes it".
   - Map the dependencies between tickets and split them by kind (`references/landing.md`): **start-after** (B needs A's result before it can begin) becomes an Orca task dep; **land-after** (B can be built on A's branch now) becomes a GitHub stack plus `orch dep` (only `orch dep` where CI runs only on PRs into the default branch), never an Orca dep.
   - Check that the repo can land in parallel: required checks on, "require branches to be up to date" off, squash merges. Add the program's shared contracts to `exclusive_paths`. If strict mode has to stay, put its cost in the digest.
   - Pick the merge policy.
   - Check the permission chain. Each card's auto-mode classifier judges every act on its own, and an instruction relayed from another session is not the human's, so the human's standing approval of this repo's merges (`orch land`) and, when the program deploys, its deploys must exist as rules in the user's `autoMode.allow`. Read `claude auto-mode config` for a rule naming this repo and the act. Missing: ask the human whether those acts are approved for the program; on yes, draft the rule with `tune-automode` ("프로젝트 지속 승인") and put its run line to the human (`orch-dash inbox add --type run_command … --key automode:<slug>`). You never edit settings yourself. Until the rule is in, merges and deploys take the ask-first path of the merge policy.
   - Create the Run with the goal as `--objective`.
   - `orch init <slug> --repo … --run … --tracker-project … --predicate <IDs> --final-check "<the real-artifact check>" --note <program note path>`. Leave out `--tracker-project` where the tracker's credentials are not in the environment: with it, every `orch status` fails; without it, `status` lists the predicate to check by hand.
   - Registering a program that has already merged PRs: `orch backfill <slug> --since <when its work began> --dry-run`, check the PRs it lists belong to the program, then the same without `--dry-run`. It adds those merges to the ledger at their merge time with their main CI result and moves `created_at` to the first one, so the cap, the rate and the dashboard count them. Never hand-edit the ledger for this.
   - `orch init` and every `orch status` start the dashboard (`orch-dash ensure`: one detached server per store, restarted when its code is older) and print its URL; give it to the human once. Nothing on it is kept by hand: every number comes from the ledger, Orca, GitHub and the tracker, so record events instead of writing status files.
2. **Verification first.** If the target repo has no `.claude/skills/verify-*`, run `create-verification-skill` in that repo before Pilot, or dispatch one worker to run it and land the skill it writes. Pilot with VERIFY driven by hand only while that skill has not landed.
3. **Pilot.** Run one worker through brief → PR → verdict → `orch land` → main green. Fix the brief, the unit size and VERIFY from whatever broke. Also confirm that the chosen worker model gets through its first `orca orchestration` call and its `orch land` without a permission prompt.
4. **Scale.**
   - Spawn the standing roles (`references/roles.md`): a main guardian, a QA lead once the first tickets land, and the machine's flow improver and resource steward unless `worker-list` shows them running. Record each with `orch record <slug> spawned --role <guardian|qa|flow|steward> --note <dispatchId>`; roles do not count against the cap.
   - Then spawn ticket workers up to the cap that `orch status` prints. The cap starts at 1, grows by one per landing proven green on main, and halves on red. The layers of one land-after chain (`orch dep`) count once, since they land as one merge; start the whole chain together.

   For each ticket worker:
   - Write the brief per `references/brief.md`. The spec starts with the ticket ID, never `/goal`.
   - Create its task with its start-after prerequisites as Orca deps (`task-create --deps '[…]'`), and start what `task-list --ready` offers, except `Land #N` tasks: those hold a human-gate decision for you, and `orch land` closes them. A land-after layer starts at once, stacked on the lower layer's branch, with `orch dep`. A prerequisite found after dispatch goes in `orch dep`.
   - Run `worker-start --task <id> --worktree new-top-level --repo <selector> --base-branch <origin/main, origin/feat/<topic> or the lower layer's branch> --name <ticket id, lowercase> --display-name "<ID> <title>" --agent claude [--model <id>]`, or `--spec "<the brief>" --deps …` instead of `--task`. The model is the program note's worker model (default: the coordinator's own); a verifier runs on another family (`--agent codex`). Run `git -C <repo> fetch origin` first: a bare `main` is the local branch, which can be landings behind. The display name is the card's durable name; the terminal tab title is the agent's own and it overwrites any rename.
   - Close its setup terminal once setup finishes: `skills-sync close-setup <card path>` in the background. The setup terminal stays a shell after its script ends, so `orca terminal wait --for exit` never fires on it. Finished setup terminals left open made Orca itself slow (22 of 50 terminals in one run). A setup stopped on a tool's trust prompt (an untrusted `.mise.toml` or `.tool-versions` in a fresh worktree) never finishes, and `close-setup` waits on it without output: before the first spawn in such a repo, trust the root Orca creates worktrees under once (`mise settings add trusted_config_paths <root>`), and read the setup terminal's screen when `close-setup` has printed nothing for a few minutes.
5. **Drain.**
   - **One inbox wait, always.** The top-level, every program coordinator and every lead keeps exactly one background inbox wait running, under `run_in_background`, and no other inbox watcher. With a program it is `orch wait <slug>`; a session without one runs `orca orchestration check --peek --wait --timeout-ms 3300000 --json`. Never both. `--peek` only looks and marks nothing read, so a session cut while it waits loses nothing. On every wake, in the same turn: act on the batch, ack it, and start the wait again. `orch wait` prints the batch and the exact `check --run <run> --ack <delivery>` line to run. A `--peek` wake carries no `deliveryId`, so take the batch with `orca orchestration check --json`, act on it, run `check --ack <deliveryId>`, and only then start the peek wait again. After a compaction, `claude --continue` or a restart, the first act is to check that this wait is alive and start it if not; a sleep loop is not a substitute. A coordinator whose wait was gone after a compaction saw lead reports only at the next heartbeat, and a coordinator that kept its old Monitor beside `orch wait` never saw a `CLOSE OUT` or `status` line again. `orch wait` wakes on worker_done, escalation, question or a worker stuck on a prompt, and acks batches that hold only heartbeats or Orca's refusals of what a released worker sent again.
   - Process every message in the batch, decide each settled worker's next owner (reuse or release), then ack.
   - On a worker's `worker_done`, in the same turn, reconcile its tickets (`use-tracker` "Reconcile": the `gh` read and the moves it supports, with the REPORT's evidence standing for `completed`; a criterion that needs checking again goes to a background subagent) and act on the `CLOSE OUT` lines `orch wait` prints beside it: release the worker; remove a finished card nobody else uses (`orca worktree rm`; checks and when to pass `--run-hooks` in `end-session` §4) unless its next task starts there; keep a failed one only for its retry. `status` lists cards you missed as `LANDED-BUT-OPEN`, and its `next` line puts them before spawning; `wait` names the released ones too, since a worker you stopped sends no `worker_done`. Leftover cards made Orca itself slow.
   - A worker closes its own session once it settles (`end-session` §7, named in every brief's REPORT); the lines below are the backstop for the ones that could not. Every return of `orch wait` also lists `SETTLED` workers nobody released (worker done or failed, no open PR, nothing unpushed): release each in that turn. A `KEEP` line names what still holds a worker; the card itself goes only after landing, as above. A `TAKEN OVER` line is a settled worker whose terminal was typed into, a `terminal send` nudge included: Orca never releases it, so run the self-check command the line carries; later wakes print only when it was asked. The session then closes itself with `end-session` or says what is left; where it has no `end-session`, close it yourself once it answers that nothing is (`orca terminal close --terminal <agentTerminalHandle>`). When the host's permission layer, not Orca, refuses `worker-release` (an auto-mode classifier has called it workload interference), stop releasing and follow "Refused acts" below (the rule: an autoMode allow for releasing this program's own workers). Do not reach the same end another way (`worker-stop`, closing its terminal, a subagent).
   - A `STUCK` line is a live worker whose screen shows a select menu, a permission prompt or a wait for input. Nobody watches a worker's terminal, so one sat for hours on its own question while the program waited; `orch wait` reads every live worker's screen each round and wakes early on a new one. Workers may ask this way; answering is your side. In that turn, yourself or through a subagent you dispatch with the line, read the question and its options on the screen and answer from what the program already decided: its briefs, standing orders and decision trail. Select the option by its number, or type the answer, with `orca terminal send` (the terminal then counts as taken over). Put it to the human at once only when no decision covers it, a call that is theirs (`orch-dash inbox add --type decision`). Record each answer and each escalation with the `orch record … signal` the line carries, the answer or the escalation in its note.
   - A permission dialog raised by a lead's workflow agent or worker takes the lead's own terminal input, so the lead cannot answer it. The layer above reads the screens of the leads and workers it started on every wake and answers such a dialog the same way when the approved scope (APPROVED lines, standing orders) covers it; anything outside goes to the human. An agent that uses a write tool guarded by a first-write confirmation hook gets, in its prompt, an instruction to invoke that policy skill before its first write, so the confirmation does not come back in every session.
   - A `STALLED` line is a worker whose ticket is open while its session has stopped writing (a turn that ended on a review report, a notification that never started a turn). `orch wait` ends early on a new one, once per 30 minutes; wake it as the line says.
   - A start that ended `outcome_unknown` with an empty composer: `worker-stop --dispatch <id>`, then `worker-start --retry-of <id> --task <task> --worktree <that card> --agent <agent> [--model <id>]` (a retry inherits neither placement nor model).
   - Record a lesson signal when the process, not the product, went wrong: `orch record <slug> signal --kind <human_correction|brief_gap|stall|tooling> --evidence <message id, PR comment URL or transcript path:line> [--ticket T] --note "<one line>"`. A human correction of how the work runs, a worker question the brief should have answered, a stall the process caused, a skill or script that misbehaved. Only record; the flow improver's rounds and Close analyze it. `land_failed`, `main_red` and failed verdicts are in the ledger already.
   - End every drain with `orch status`; its lines are how a drain ends. `status` also prints what only the dashboard's collector sees: `STALLED` workers (turn ended with the task open, no session activity since dispatch, one tool call running too long), `SPARE` slots with ready tasks, and `LEDGER GAP`s. Act on them like the other lines. `orch-dash note` records a risk or decision the dashboard should show.
   - Under `/goal`, a running background task defers the Stop hook's goal check. If the hook re-prompts anyway with no new event, answer in one line with no tool call. If it fires back-to-back, switch to a foreground `orch wait <slug> --rounds 1 --timeout-ms 540000` (Bash timeout 600000).
6. **Triage.** Workers report findings with a proposed class in `worker_done` and file nothing (`references/brief.md` FORBIDDEN). Classify each one yourself against the predicate:
   - NOW: it blocks a named predicate item, or it is a reproduced correctness, security or data defect in code this program merged. File it in the follow-up format (`use-tracker`), then `orch record <slug> admitted --ticket X` naming the item or defect. An admitted ticket blocks Close like a predicate item: `orch status` lists it as open until it is done or canceled.
   - LATER: one line on the program note's `보류` list with its revisit trigger. No ticket.
   - DROP: one line in the digest with the reason. No ticket.

   A follow-up someone else already filed (a reviewer, the human, a worker on an old brief) gets the same classes: NOW is `record admitted`, LATER is `record parked` plus its line on `보류`, DROP is canceled with the reason as a comment. At every digest, compare the admitted set with the last one; for each admission since, name the predicate item it serves, or move it to LATER.
7. **Land** (`references/landing.md`). Workers land their own PRs with `orch land`:
   - Normal PRs land in parallel the moment they are ready.
   - Migrations, CI files and other `exclusive_paths` land one at a time, on the latest base.
   - Dependencies land first.

   You keep it honest:
   - start-after edges in Orca, land-after chains stacked with `orch dep`
   - `STALE` PRs unstuck
   - classes set (`record reprioritized`)

   You land only under human-gate, after the Orca gate resolves, and for a PR whose review outlasted its worker. `orch wait` lists those every wake: `WAITING ON REVIEW` for each still short of ready, and `LAND #N` with its command once one is approved (and through the human gate under human-gate), `CLEAN`, green at its head, free of unresolved threads and not on hold. Hold one when the human or the ticket says to wait, or a `deliver-ticket` §6 "Ask first" case applies: `orch record <slug> parked --pr N --note <why>`, released by `record admitted --pr N`. `MERGED OUTSIDE LAND #N` is a PR someone merged by hand: run the `orch landed` it carries instead, then finish its ticket the same way. Run that `orch land` in the background, then finish the ticket the way the worker's `deliver-ticket` §6 would: read main CI's log and any apply or deploy run the merge started, move the ticket (`use-tracker` "Reconcile"), and cancel a reminder sent for that review, or answer it with the merge where it cannot be cancelled. A land that refuses, or a §6 "Ask first" case, goes to the human as a decision.
8. **Verify main.**
   - The lander watches its merge's main CI and records `main_green`.
   - Red main belongs to the main guardian: flake check, freeze, hotfix or revert, notify (`references/roles.md`). While main is red, only `--class main-fix` lands.
   - The QA lead verifies each landed ticket and audits design against code. It also runs the E2E suite on main every 5 landings, every 2 h, and before each gate PR.
   - When the QA lead or a worker reports that `verify-<app>` could not drive a feature, or described it wrongly (`verify skill stale`), dispatch a worker to run `maintain-verification-skill` on that repo.
9. **Close.**
   - When `status` says the tickets are done, run the predicate's final check on the real artifact: the QA lead drives `verify-<app>` on main, or, without a QA lead, you run the program's `final_check` on a fresh `origin/main` checkout (`git archive` into a scratch directory), never on a worker's tree.
   - `orch record <slug> predicate_verified --note <evidence>`.
   - Release the standing roles: `orca orchestration send --to dispatch:<the role's dispatchId from its spawned record> --subject release --body "program closing: send worker_done"`, then `worker-release` once its `worker_done` arrives (Orca releases only settled workers). Release any remaining workers and remove any worktree still left (checks and `--run-hooks` in `end-session` §4).
   - The program ends only when `orca orchestration worker-list --run <run> --terminal-state reclaimable --json` returns no rows. That is Orca's own end condition: every settled worker has been released or retained. Release what it lists.
   - The dashboard server is detached and serves every program, so it neither needs stopping nor defers the `/goal` stop check. `state.json` stays for later reading.
   - Run `measure-delivery`, save its output as `~/.claude/programs/<slug>/reflect/delivery.md` for `reflect`, and audit the trail per `show-me-your-work`.
   - Run `reflect` in program mode. It turns the signals and the ledger's failures into lessons in the lessons ledger, fills in whether earlier lessons held, and opens at most one draft PR against `agent-skills` for the lessons that recurred. Put its digest lines and the PR link in the digest; the human approves and merges. Run it even with no signals and no failures: it then only records that the applied lessons held, and the digest gets one line saying so.
   - Neither step is skipped for a brief's MODEL CALLS line: `measure-delivery` only reads, and `reflect` is the model call Close exists for. The signals are yours to fold in here unless a flow improver you spawned is running; leaving them to one that does not exist drops them.

## How the human's words change the program

| The human says | Do, in the same turn |
|---|---|
| "I'll watch X myself, don't bother" (usage, a metric, a channel) | Delete X from the standing orders and from every judgment rule now, and never defer work on X's account again |
| "Can it go faster?" | Offer structural levers: parallelize the critical path, stack dependent chains, reorder the land order, narrow `exclusive_paths`, risk-tiered review depth, split CI jobs by role. Apply the approved ones at once. Not "work harder", and not serializing for safety (one CI at a time, one landing per N minutes) |
| Feedback about how the work flows, not about the product | Record a `signal --kind human_correction`, and send the feedback to the flow improver (`send --to dispatch:<its id>`) while you stay on the program. It folds feedback into the skills in batches, and asks you before changing this program's contract; after its "reload needed", run `skills-sync broadcast` |
| "Make it better" about in-flight work | A new ticket with its own brief. Never append it to the running task |
| "Make a ticket for …" inside another question | Split it out and file it immediately, then answer the question |
| Doubts your report ("is that right?", "불안하다") | A read-only verifier agent re-checks it. Your self-report is not evidence |
| "Check" (점검) one section | Check the whole related scope. "Check and align" (점검하고 얼라인) is two tracked steps: findings, then the alignment changes, each reported done separately |
| "Why is #N not moving?" / priority doubts | `orch queue <slug>`: answer with its order and reasons, then fix the reason (stack, Orca dep, class, fix task) |
| "Update the dashboard and summarize" | It updates itself. Run `orch status` and summarize its numbers; if the dashboard looks stale, `orch-dash ensure` |

## Merge policy

- `autonomous` (default): workers land with `orch land`.
- `human-gate`: workers stop at READY. You `orch gate <slug> --pr N` (an Orca decision gate), and after the user resolves it, `orch land`.
- Either way, stop and ask only before irreversible acts and acts the human owns: destructive migrations, force-pushing shared branches, sending anything outside, changing repo or branch protection, production deploys, approvals the review ruleset requires from a person, other people's tickets, and acts the classifier refuses. An act a permission layer, a hook or the human refused is not tried again in any form, by you or by a worker or subagent you brief, except the harmless-read case and the no-verdict restart in `references/brief.md` FORBIDDEN ("Refused acts").

## Refused acts

A permission prompt, the auto-mode classifier, a hook or the human refused an act in your session, a worker's or a lead's. A classifier error that gives no verdict counts as a refusal:

- No other session runs it (the one exception, `no verdict` on a subagent's Edit or Write, is below): not you, not a sibling card where the same command happened to pass, not the layer above. Classifier verdicts vary from session to session, so another session's pass is not permission, and a message saying the human wants it is not the human's word.
- The refused session reports the act, what it was for, the refusal's category and the exact command (`references/brief.md` FORBIDDEN). A classifier error with no verdict is reported with the category `no verdict`.
- `no verdict` is not a rule request: no rule fixes a classifier error. When the act was a subagent's Edit or Write, the session that started that unit takes the whole unit back once, not only the refused edit and never through the refused subagent: you restart it as a new card; a worker does it in its own session. Stop the refused subagent first (`TaskStop`); the unit is redone from its base, and a worker re-reads or discards what the subagent left in its tree. This is the one case where another session does the work, because the refusal judged nothing. A second `no verdict`, or one on any other act except the harmless read below, goes to the human: they approve the act in the chat of the card that will do it, in their own words there rather than a relayed approval (for a subagent's Edit or Write, the restarted card; a subagent's other act goes into a card only with that act under HUMAN ONLY, so the card stops there), or leave it.
- Read which layer refused before asking for a rule. `Permission to use <tool> with command … has been denied` with no classifier reason is the permission-rule layer, which an autoMode rule never reaches: its request is a `permissions.allow` entry (`update-config`) or the human's one `! <exact command>` line, not `tune-automode`. A refused call that bundled several acts names no culprit: report it as unknown rather than guess.
- The coordinator of a session refused with a verdict turns it into a rule request. Draft the smallest rule for that act class on this repo with `tune-automode`, put its run line to the human with `orch-dash inbox add --type run_command --title "권한 규칙 필요: <repo> <act> (--apply 없이 돌리면 diff 만 보인다)" --command "<emit's run line without the leading !>" --key denied:<repo>:<act>`, and say in your reply: "<card>에서 <act>가 분류기에 거부됐습니다(<category>). 다른 세션이 대신 실행하면 거부를 우회하는 것이라 하지 않습니다. 계속 허용하려면 규칙을 추가해 주세요: <rule>. 실행: `! <run line>` (설정을 백업한 뒤 적용하고, 되돌리는 명령을 출력합니다). 적용되면 <card>가 같은 행동을 한 번 다시 합니다."
- Once the human has run it, or approved the act in the refused session's own chat (for a production sync only the rule counts: `references/top-level.md`), that session does the act once more, after you check the new rule sits in the layer that refused. A running session may need a restart before a new rule reaches it: close it through Orca (`orca terminal close`, not a typed `/exit`, which a nudge can turn into prompt text), confirm it is gone, then start the new one; two sessions never share a worktree. This is not a retry of the refusal: its cause is gone.
- A harmless read refused as something it does not do, or with no verdict, is the harmless-read case in FORBIDDEN. When a read refused as something it does not do comes back, request an `environment` or `allow` rule for it as above; a `no verdict` read that comes back goes to the human.
- Do not tell the refused session a form that would pass (the value on stdin instead of an argument, a wrapper script, a sibling session, Bash after Edit got no verdict): coaching the workaround is the workaround. A refused check is recorded as unverified (refused), and the work goes on without it.
- A change made around a refusal anyway (another tool, a script: a FORBIDDEN breach) does not land as it is. Refused with a verdict: the change is reverted and goes the rule-request way above. Refused with `no verdict`: a subagent's unit is redone from its base by the session that takes it back (above); a session's own edit is re-applied with Edit or Write, and re-read, only after the human approved it there. Either way the PR body says which edits were first made another way: tests can pass on such a change and miss what a re-read finds.
- A card that stops because the act was never in its first prompt's approval is a scope gap, not a rule gap. Do not send it "사용자 승인" by message (refused as relayed: a rename, a workflow dispatch, a merge), do not press its keys, do not do the act yourself, and do not ask the human to type it into the card. If the human already approved it, start a new `/goal` card whose APPROVED line carries it (`dispatch-card` §2); if not, ask once, and on yes start that card.

## What reaches the human

The dashboard, plus the digest line in the program note, batched.

Inside the scope the human approved (the standing orders, a brief's APPROVED line), you and the layers under you decide: take the recommended default, act, and report what was chosen. Restarting an app, a language or settings change, an upgrade, checking a recording are such decisions; asking each of them sent the human dozens of questions in one day. The human gets only two kinds: what only they can do (a permission dialog outside the approved scope, a login, a payment, a document submission), and an irreversible or outward act outside that scope. Those go out together in one message, not spread across the day. That message, and every status report to the human, is laid out with the `brief` skill; its per-item stage table is the `orch stage` record, each cell written when you verify it (`references/dashboard.md`, "The stage table").

A decision you wait on the human for is also registered with `orch decide add` and closed with `orch decide done` the moment the human answers or settles it in words; a dashboard button, or a prompt that starts with the id or a unique option label (the `UserPromptSubmit` hook), closes it itself (`references/top-level.md`, "Asking the human"). The digest holds open gates, a proposed predicate, irreversible acts, and any standing order that contradicts reality. Never retries, CI flakes, review-thread triage, rebases, "should I continue", or implementation-policy questions (design options, ticket splits, stack or parallel): a self-review subagent decides those from the human's own precedent (how they handled it before, how they review, the shape of projects they already shipped), never picking an option of a different shape (a new architecture, tool or process), and you record the decision in `decisions.tsv` with that precedent as its evidence. A question no precedent covers becomes a decision for the human (`orch decide add`) while the rest of the program keeps moving.

## Where this differs from Orca, and why

Orca's `orchestration` skill is the default; these are the places a program overrides it on purpose.

| Orca says | This skill does | Why |
|---|---|---|
| Start the full independent wave before waiting | Ticket workers start at a cap of 1 that grows by one per landing proven green on main and halves on red | The pilot fixes the brief, unit size and VERIFY before they are copied; past what main CI and the land lanes absorb, more workers only grow the landing backlog (`references/landing.md`: stop starting, start finishing) |
| Pass `--model` only when the user named one | `--model` is the program note's worker model, by default the coordinator's own | The pilot proves that model reaches its first `orca orchestration` call and `orch land` without a permission prompt, and the note keeps a resumed coordinator on the same model; the user's agent default can change under a running program (`/model` changes it globally) |
| Share the current workspace; a new worktree only on a real checkout conflict | One `new-top-level` worktree per ticket | Each ticket is its own branch and PR landing in parallel, stacked or on `origin/main`; a shared checkout would mix their branches |
| The coordinator's turn ends only on its report to the user | `orch wait` runs in the background and the turn ends while it waits | A program outlives any one turn: the wait wakes you on worker_done, escalation or question and acks heartbeat-only batches, and under `/goal` it defers the Stop hook's check. Orca's end condition still closes the program (Close) |
| `worker_done` body is three sentences | The brief's REPORT asks for the PR URL, merge commit, reviewers, the VERIFY output seen, the main-CI run and the findings with their proposed class | That body is the landing's evidence and the only channel for what a worker must not write outside its worktree; the coordinator records it |
| `terminal send` only for prompts that need no task state or inbox | One exception: after the content goes through `orchestration send --to dispatch:<id>`, a one-line `terminal send` nudge ("run your orchestration check") to a worker whose turn ended | `send` does not wake an idle agent; a worker sat 80 min on an answered blocker. The content stays in Orca's tracked mail; a worker without a terminal gets Orca's recovery instead. A nudged terminal counts as taken over: `worker-release` refuses it from then on, and it closes through the `TAKEN OVER` self-check |

## Traps seen in real runs

| Trap | Instead |
|---|---|
| A coordinator granting each merge | Workers land through `orch land`. The coordinator became the slowest lane |
| "Whoever is ready lands next" | Dependencies in Orca, and the land order for the exclusive lane. A dependency root starved for 5h behind newer PRs |
| One merge baton under strict up-to-date branches | A parallel normal lane with strict off. Every landing had pushed every other PR behind for another 30–40 min of CI |
| Landing a dependency chain one PR at a time (rebase + CI between each) | Stack it; the top's `land` merges the chain in one `merge-async` |
| Workers idling for hours "waiting for the merge slot" with nothing to do | `land --wait-minutes` in the background. `status` STALE lines and backlog hours make the wait visible and actionable |
| A worker calling `gh api … merge-async` itself and the classifier refusing it as "Merge Without Review" | Merges happen only inside `orch land`, which is the review gate and the allowed command |
| Reverting every red main by reflex, or the coordinator debugging it | The main guardian: flake check first, then hotfix or revert by the rule in `references/roles.md` |
| Cards named by Orca's automatic title, one unrelated to the ticket | `--display-name "<ID> <title>"` on every start; a terminal rename does not stick |
| A `worker-start` spec starting with `/goal` | Start the spec with the ticket ID; Orca already delivers it as the worker's task. A card from `orca worktree create` is the opposite: `/goal` plus its brief (`dispatch-card` §2) |
| Waiting with `sleep`, a hand-built watcher, or invented `orca … events/status` | The one inbox wait (Drain). One empty wait is a checkpoint; after three, run `worker-list --run` |
| Nudge-only turns ("You have N orchestration messages") burning coordinator turns | End such a turn with no tool call; real work arrives through `orch wait` |
| A worker shows `live` but has done nothing for many minutes | It may be sitting on a permission prompt (`status` lists `idle-waiting`): `worker-read --dispatch <id> --source terminal`. Answer it inside the approved scope as for a `STUCK` line; outside it, put it in the digest for the human. Waiting output does not prove the agent stopped, so do not stop or retry it |
| A worker that sent a blocker as a status and ended its turn sat 80 min after your `send` answered it | `send` does not wake an idle agent. Send the answer with `orca orchestration send --to dispatch:<id>` so Orca tracks it, then nudge the terminal with one line, `orca terminal send --terminal <agentTerminalHandle> --text "run your orchestration check" --enter`, and read the terminal until the turn starts (text left in its input box needs Enter alone, `--text '' --enter`, not the text again); that terminal later closes through its `TAKEN OVER` self-check, not `worker-release`. Never put the content itself in `terminal send`: Orca keeps no record of it. A worker with no terminal (terminal verbs refuse its handle) follows Orca's recovery instead: a transcript (`worker-read --source transcript`) whose last turn sent no `worker_done` is Orca's proof it stopped, so read `orca skills get orchestration --reference references/recovery-and-cleanup.md` and choose `worker-stop` or `worker-abandon` |
| A handoff prompt that retypes the rules | The note is the handoff; the prompt is one line |
| Follow-ups spawned the moment they are filed | Park them; `status` shows derived tickets per predicate item |
| Parallel CI jobs named `1/3 2/3 3/3` | Name jobs by what they check (typecheck, lint, unit, db, api…) |
| Several cards running docker compose stacks and image builds at once; the machine and the Orca UI crawled | Heavy local runs go through `orch heavy`, 2 machine-wide slots (`landing.heavy_slots`) |
| Finished setup terminals and landed cards left open (50 terminals; 8 cards after one compaction dropped the step) | `skills-sync close-setup` on every new card; act on the `CLOSE OUT` lines in the turn a worker reports done, and on the `SETTLED` and `TAKEN OVER` lines every wake prints |
| A worker that finished but had no capability token to send `worker_done` stays `active`, and no sweep line names it | Ask it the `TAKEN OVER` self-check; its answer is its REPORT, and you close it out |
| A shared state file overwritten in place and left empty | Append-only ledger; anything else is written to a temp file and renamed |
| Typing `/model` into a worker terminal | Pass `--model` to `worker-start`; `/model` changes the global setting |
| A check needs a secret the worker's session did not inherit from the environment | The worker writes a script that reads the value from the environment and prints only the result, never the value; the coordinator reads it, runs it in its own terminal and sends the output back. Only for a value that is missing: a check a guard refused follows "Refused acts" |
| A worker that has run for hours keeps hitting inference gateway 5xx errors or timeouts; its context is too large, and `/compact` is as heavy | Replace it, do not retry it in place: the layer above reads its worktree (branch, commits, what is unpushed), writes a fresh brief with what is done and what is left, starts a new worker on that card, and releases the old one |

## Resume (handoff)

The new coordinator's whole prompt is two lines, `/goal orchestrate resume <slug>` and `ROLE: lead <slug>`; the second binds the program to that session for the reorient hook. A session started with `claude --agent agent-skills:lead --name lead:<slug>` needs only the first. On resume:

1. Read the program note.
2. `orca orchestration run-use --id <run>`.
3. Make `program.json` match the note: `orch set <slug> merge_policy|ceiling|deadline|predicate|exclusive_paths …` for any difference. The note wins.
4. `orch status`.
5. Stop any inbox watcher the program ran before (a Monitor, a script), start the one `orch wait`, and continue at Drain.

After an automatic compaction, the plugin's SessionStart hook tells a declared lead to do steps 1 and 4 again. Before them, check that the inbox wait is alive and start it if not (Drain, "One inbox wait, always").

Whenever the note's policy, ceiling, deadline, predicate or exclusive paths change mid-run, mirror them with `orch set` in the same turn. Workers report to the Run inbox, not to a session name, so nothing needs re-pointing. The old coordinator ends only after the new one has printed `status`.
