# Program mode: a lead's steps

A lead reads this file now, before its first step. The orchestrator runs none of these steps; it reads a section here when SKILL.md or `top-level.md` points to it, or when a trap below fits the cards it started. What both modes share stays in SKILL.md: the core rules, Roles, Stay answerable, Drain (step 5), Merge policy, Refused acts and What reaches the human.

## Steps

1. **Frame.**
   - Read every ticket in scope.
   - Write the predicate as countable ticket IDs plus a final check on the real artifact ("ABC-1, ABC-2, ABC-3 Done and `verify-<app>` drives the quickstart on main"). Derive it yourself. If the tickets have no countable end, write your best predicate, mark it proposed in the digest, and go on. The predicate is the program's exit condition (principle **Work to an Exit Condition**): write its out-of-scope list beside it in the program note, and report progress as "N/M predicate items done", never as tickets filed.
   - Copy the human's goal into the standing orders verbatim, one sentence per order. A sentence that would have a worker write outside its worktree stays verbatim in the lead's list, and the workers' list gets its worker form: "put it in the worker_done body; the lead writes it".
   - Map the dependencies between tickets and split them by kind (`references/landing.md`): **start-after** (B needs A's result before it can begin) becomes an Orca task dep; **land-after** (B can be built on A's branch now) becomes a GitHub stack plus `orch dep`, never an Orca dep. Two units that change the same path are land-after too, even when neither needs the other's result: the first to merge leaves the other in conflict, and the fix push dismisses its approval. So write each unit's paths in its brief's SCOPE, and never run two units on one path, or under one `exclusive_paths` glob, as parallel PRs on the same base.
   - Check that the repo can land in parallel: required checks on, "require branches to be up to date" off, squash merges. Add the program's shared contracts to `exclusive_paths`. Set `visual_paths` to the files that render (`orch set <slug> visual_paths …`): its default globs are fnmatch, where `*` crosses `/`, so `apps/web/*` also catches test fixtures and `packages/ui/*` a README. When `land` flags a non-screen path again, narrow the knob once instead of asking the human for a `no-visual-change` label per PR. If strict mode has to stay, put its cost in the digest. A repo with no CI workflows at all never passes `land` until the human declares it in `orchestrate.no_ci_repos` (the no-CI lane, `references/landing.md`): no checks otherwise counts as pending, and a worker sits in a `land` wait that can only yield. Hand them the `skills-config` line; until they run it, briefs on that repo stop at READY.
   - Read the target repository's data-sharing restrictions. Carry them into the digest and every brief's FORBIDDEN section; every reviewer and tool must stay within the permitted boundary. No permitted reviewer means review pending, never a model-specific exception.
   - Pick the merge policy.
   - Check the permission chain. Each card's auto-mode classifier judges every act on its own, and an instruction relayed from another session is not the human's, so the human's standing approval of each outward act the predicate needs must exist as a rule in the user's `autoMode.allow`: this repo's merges (`orch land`), its deploys when the program deploys, and edits to tracker items or PRs an earlier session made (a body patch, retitle, `gh pr edit`): the default soft-deny covers items the acting session did not create, so these are refused while new tickets, relations and comments pass. Read `claude auto-mode config` for a rule naming this repo or tracker project and the act. Missing: ask the human whether those acts are approved for the program; on yes, draft the rule with `tune-automode` ("Standing project approval") and put its run line to the human (`orch-dash inbox add --type run_command … --key automode:<slug>`). You never edit settings yourself. Until the rule is in, those acts take the ask-first path of the merge policy.
   - Bind this terminal to the program's Run: run `orch doctor`. Only when it says this terminal is bound to no Run, `run-create --objective "<the goal>"` (or `run-use --id <run>` when resuming), then `orch doctor` again to confirm. Workers report to it, and only a bound terminal gets their mail typed in (`references/top-level.md` "Your Run").
   - A lead started as a dispatched worker binds nothing: Orca refuses a worker binding the Run it works for. `orch doctor` names that Run and your dispatch; that Run is your `orch init --run`. Your workers start on it and report to your Dispatch mailbox, Orca's notice wakes you for their mail, and `orch init` records your dispatch, so `orch wait` reads your own mailbox and every `orch` command sees only the units under you.
   - `orch init <slug> --repo … --run … --tracker-project … --predicate <IDs> --final-check "<the real-artifact check>" --note <program note path>`. Leave out `--tracker-project` where the tracker's credentials are not in the environment: with it, every `orch status` fails; without it, `status` lists the predicate to check by hand.
   - `--repo` takes one repository. `orch verdict`, `land` and `landed` look PRs up only there, and `main_green` or `main_red` is accepted only for a merge `landed` recorded. `orch init` takes no second repository (a second `--repo` is ignored), so either run one lead per repository, or name each unit in another repository, with its repository, in the program note beside the predicate. Such a unit's brief replaces the template's LAND with its own: the same review, unresolved-thread and required-check conditions, how its PR lands (`READY-WAIT: <kind>`, who merges, how the merge is verified), and no `orch verdict`, `land`, `landed`, `main_green` or `main_red`. Its worker_done body carries what the ledger cannot: the verdict (reviewed head sha and its source) and main CI's result on the merge commit. That replacement is the one exception to pasting the template's LAND whole, and the brief's APPROVED line then names the same merge path instead of `orch land`, with the human's words that approve it.
   - Registering a program that has already merged PRs: `orch backfill <slug> --since <when its work began> --dry-run`, check the PRs it lists belong to the program, then the same without `--dry-run`. It adds those merges to the ledger at their merge time with their main CI result and moves `created_at` to the first one, so the cap, the rate and the dashboard count them. Never hand-edit the ledger for this.
   - `orch init` and every `orch status` start the dashboard (`orch-dash ensure`: one server per store, restarted when its code is older; with an old macOS LaunchAgent from `orch-dash install-agent` loaded, launchd runs it and `ensure` only hands over to launchd; the `orch-dash` Orca automation, `skills-sync setup enable orch-dash`, runs `ensure` every 10 minutes) and print its URL; give it to the human once. Nothing on it is kept by hand: every number comes from the ledger, Orca, GitHub and the tracker, so record events instead of writing status files.
2. **Verification first.** Choose a harness or direct checks that prove the predicate on the real deliverable. Reuse an existing verification skill when suitable; create one only when useful within the authorized scope. Record the exact VERIFY commands before Pilot. The checks must cover every acceptance criterion regardless of packaging. Report a stale existing skill or harness, repair it within scope, and prove any uncovered criterion with direct checks; do not silently skip it.
3. **Pilot.** Run one worker through brief → PR → verdict → `orch land` → main green. Fix the brief, the unit size and VERIFY from whatever broke. Also confirm that the chosen worker model gets through its first `orca orchestration` call and its `orch land` without a permission prompt.
4. **Scale.**
   - Spawn the standing roles (`references/roles.md`): a main guardian, a QA lead once the first tickets land, and the machine's flow improver and resource steward unless `worker-list` shows them running. Record each with `orch record <slug> spawned --role <guardian|qa|flow|steward> --note <dispatchId>`: Orca has no field for a role, and roles do not count against the cap. A ticket unit needs no such line (`references/brief.md`, "Single worker").
   - Then spawn ticket workers up to the cap that `orch status` prints. The cap starts at 1, grows by one per landing proven green on main, and halves on red. The layers of one land-after chain (`orch dep`) count once, since they land as one merge; start the whole chain together.

   For each ticket worker:
   - Write the brief per `references/brief.md`, its FORBIDDEN copied whole from the current template, never shortened by hand. The template sentences of LAND and VERIFY are pasted the same way, untranslated, with only `<slug>`, ticket and PR filled in, since a translation drops the clause a gate or exception rests on and a copied line can carry another program's slug. A spec you write by hand starts with the ticket ID, never `/goal`; the spec `skills-sync card` composes from a brief file keeps the brief's `/goal` line, which states the goal even where Orca's preamble keeps it from running as a command.
   - A shared brief (`briefs/_common.md`) holds copies of the template's paragraphs, and a reload reaches sessions, never briefs already written. After a `skills-sync broadcast` that changes `references/brief.md`, paste the changed FORBIDDEN, LAND or PEERS paragraphs into it and send them to the live workers, or they treat a form the new text allows as refused.
   - Create its task with its start-after prerequisites as Orca deps (`task-create --deps '[…]'`), and start what `task-list --ready` offers, except `Land #N` tasks: those hold a human-gate decision for you, and `orch land` closes them. A land-after layer starts at once, stacked on the lower layer's branch, with `orch dep`. Before each start, `orch overlap <slug> --paths <its SCOPE paths>`: an `OVERLAP plan #N` line makes the unit land-after #N, so it starts stacked on #N. After PRs open, an `OVERLAP #A #B` line in `orch status` means the same for two open PRs: B merges A's branch, settling the conflict before review, and is stacked on A with `orch dep`, by the commands the line prints. An `OVERLAP <other-slug> …` line names another program's PR: no stack and no `orch dep`; settle the order through PARENT (`references/top-level.md` "Leads that depend on each other"). A prerequisite found after dispatch goes in `orch dep`. A lead started as a dispatched worker cannot create tasks or gates on the Run it works for (`worker_cannot_coordinate_own_run`): it starts each unit with `--spec` once its prerequisites have landed, and its decisions go to `orch decide add`.
   - Once the program has a Run, every new unit starts with `worker-start`, never `orca worktree create --prompt` or `dispatch-card`, even when the cards you adopted at the start are `/goal` cards (the reason: SKILL.md "Stay answerable", "You write no PR").
   - Run `worker-start --task <id> --worktree new-child --repo <selector> --base-branch <origin/main, origin/feat/<topic> or the lower layer's branch> --name <ticket id, lowercase> --display-name "<ID> <title>" --agent claude [--model <id>]`, or `--spec "<the brief>" --deps …` instead of `--task`. The model is what `orch model worker` prints, or the program note's when the human named one; with neither, leave `--model` out. A verifier runs independently of the implementer with the configured agent. Run `git -C <repo> fetch origin` first: a bare `main` is the local branch, which can be landings behind. The display name is the card's durable name; the terminal tab title is the agent's own and it overwrites any rename. Your own dispatch keeps the workers' one-act-per-call rule: the brief saved with Write first, then each `worker-start` in a Bash call of its own, with no brief write or other start beside it, so a refusal names its act and does not stop the other dispatches.
   - Close its setup terminal once setup finishes. `skills-sync card` and `skills-sync handoff` start `skills-sync close-setup <card path> --agent <handle>` in the background themselves and print its log path; a raw `worker-start` or `orca worktree create` needs it run by hand, in the background. The setup terminal stays a shell after its script ends, so `orca terminal wait --for exit` never fires on it. Setup terminals left open slow Orca itself. The log ends in `result: failed` when the agent sits on a trust or permission dialog or shows no start. A setup stopped on a tool's trust prompt (an untrusted `.mise.toml` or `.tool-versions` in a fresh worktree) never finishes, and `close-setup` waits on it without output: read the setup terminal's screen when the log has said nothing for a few minutes, and surface the prompt as `references/top-level.md` "Starting a worker" says, never accept it: trusting that file runs its code.
5. **Drain** is in SKILL.md: the orchestrator runs it too.
6. **Triage.** Workers report findings with a proposed class in `worker_done` and file nothing (`references/brief.md` FORBIDDEN). Classify each one yourself against the predicate:
   - NOW: it blocks a named predicate item, or it is a reproduced correctness, security or data defect in code this program merged. File it in the follow-up format (`use-tracker`), then `orch record <slug> admitted --ticket X` naming the item or defect. An admitted ticket blocks Close like a predicate item: `orch status` lists it as open until it is done or canceled.
   - LATER: one line on the program note's `보류` list with its revisit trigger. No new ticket. Work that will be done when a date or condition comes is not LATER: it is a to-do on the board (`orch board todo add`, `brief` skill). The trigger is an event a named role fires (the QA lead's next pass, the human's release decision, a ticket that flips a flag), never a condition nobody watches; when an existing ticket or PR performs the trigger, the revisit line goes on it too. A security, authorization or data-exposure suspicion that touches a program invariant gets a reproduction attempt first, and is LATER only when that attempt did not reproduce it (a reproduced one is NOW, above).
   - DROP: one line in the digest with the reason. No ticket.

   A follow-up someone else already filed (a reviewer, the human, a worker on an old brief) gets the same classes: NOW is `record admitted`, LATER is `record parked` plus its line on `보류`, DROP is canceled with the reason as a comment. At every digest, compare the admitted set with the last one; for each admission since, name the predicate item it serves, or move it to LATER.
7. **Land** (`references/landing.md`). Workers land their own PRs with `orch land`:
   - Normal PRs land in parallel the moment they are ready.
   - Migrations, CI files and other `exclusive_paths` land one at a time, on the latest base.
   - Dependencies land first.

   You keep it honest:
   - start-after edges in Orca, land-after chains stacked with `orch dep`
   - `STALE` PRs unstuck
   - classes set (`record reprioritized`)

   A card lands its own PR: independent review Act-on 0, zero unresolved threads, required checks green or the no-CI lane, then `orch land`, `main_green`, `end-session` §7. You hold the judgment and the order (land-after, `exclusive_paths`, holds), and each card that lands carries the merge in its first prompt's APPROVED line (`references/brief.md`). A card with no such line stays at READY for the session above. You land only under human-gate, after the Orca gate resolves, and for a PR whose review outlasted its worker. `orch wait` lists those every wake: `WAITING ON REVIEW` for each still short of ready, and `LAND #N` with its command once one is approved (and through the human gate under human-gate), `CLEAN`, green at its head, free of unresolved threads and not on hold. Hold one when the human or the ticket says to wait, or a `deliver-ticket` §6 "Ask first" case applies: `orch record <slug> parked --pr N --note <why>`, released by `record admitted --pr N`. Every land hold you tell workers about (a serialized window, a hold until a fix lands) is recorded this way for each PR it covers, so `land` refuses it; the message only says why. A hold sent only as a message misses a worker spawned after it and a background `land` loop that does not read its inbox. `MERGED OUTSIDE LAND #N` is a PR someone merged by hand: run the `orch landed` it carries instead, then finish its ticket the same way. Run that `orch land` in the background, then finish the ticket the way the worker's `deliver-ticket` §6 would: read main CI's log and any apply or deploy run the merge started, move the ticket (`use-tracker` "Reconcile"), and cancel a reminder sent for that review, or answer it with the merge where it cannot be cancelled. A land that refuses, or a §6 "Ask first" case, goes to the human as a decision.
8. **Verify main.**
   - The lander watches its merge's main CI and records `main_green`. A watcher that exits, or a lookup or API call that fails, leaves main unknown, never red: `main_red` is recorded only after `gh run view <id> --json status,conclusion` shows the run completed with a non-success conclusion (`references/landing.md`, main CI). The no-CI lane has no run to read: its VERIFY commands at the merge commit decide.
   - Red main belongs to the main guardian: flake check, freeze, hotfix or revert, notify (`references/roles.md`). While main is red, only `--class main-fix` lands.
   - The QA lead verifies each landed ticket and audits design against code. It also runs the E2E suite on main every 5 landings, every 2 h, and before each gate PR.
   - When the QA lead or a worker reports that `verify-<app>` could not drive a feature, or described it wrongly (`verify skill stale`), dispatch a worker to run `verification-skill` in maintain mode on that repo.
9. **Close.**
   - When `status` says the tickets are done, run the predicate's final check on the real artifact: the QA lead drives `verify-<app>` on main, or, without a QA lead, a verifier worker runs the program's `final_check` on a fresh `origin/main` checkout (`git archive` into a scratch directory), never on a worker's tree. That verifier's brief is written like a ticket worker's (step 4).
   - `orch record <slug> predicate_verified --note <evidence>`. Before it, re-run each ticket's motivating observation. The note lists each final-check probe as ran, failed or unrun, and names which branches of a multi-branch change were exercised. A failed or unrun probe (a pressure-gate `gave_up` included) makes the outcome PARTIAL, never `predicate_verified`; a probe that passed only through a bypass or a substituted condition counts as failed. A `보류` line records an unrun probe and never turns PARTIAL into verified. Each unexercised branch gets a provoke step on dev or local, or a `보류` line with its revisit trigger and the stand-in tried (a local VM, a privileged container, a sandbox repo) and why it fell short. A Close counter-review or audit brief quotes this paragraph so the reviewer checks the closing rule itself, not only the classification.
   - Release the standing roles: `orca orchestration send --to dispatch:<the role's dispatchId from its spawned record> --subject release --body "$(cat <file>)"`, the body ("program closing: send worker_done") in a file written with the Write tool as for every message body (`references/top-level.md`, "Talking to sessions"), then `worker-release` once its `worker_done` arrives (Orca releases only settled workers). Release any remaining workers; a worktree still left is the cleaners' (`end-session`, "Who cleans up").
   - The program ends only when `orca orchestration worker-list --run <run> --terminal-state reclaimable --json` returns no rows. That is Orca's own end condition: every settled worker has been released or retained. Release what it lists.
   - The dashboard server is detached and serves every program, so it neither needs stopping nor defers the `/goal` stop check. `state.json` stays for later reading.
   - Each check left for later (a `보류` line, a check deferred to a later scheduled run) gets an owner before Close: a scheduled check, a standing-loop item or a ticket, named in the digest. A digest line alone owns nothing. For a human owner: `orch board later add <title> --trigger <condition> --who <owner>`, and the digest names the board key. A ticket ID written into a decision, audit or owner report is read from the tracker with its title beside it (CONTEXT in `references/brief.md`), and a correction goes to everyone who already received the wrong one.
   - Audit the trail per `show-me-your-work`, writing with the Write tool and later sections with Edit, never a Bash heredoc (audit text quotes commands that secret-scanning hooks match).
   - Run `reflect` in program mode, once. Its pack step runs the delivery measurement (reflect's measure mode) once and saves it as `~/.claude/programs/<slug>/reflect/delivery.md`; Close does not measure separately. It turns the signals and the ledger's failures into lessons in the lessons ledger, fills in whether earlier lessons held, and opens at most one draft PR against `agent-skills` for the lessons that recurred. Put its digest lines and the PR link in the digest; the human approves and merges. Run it even with no signals and no failures: it then only records that the applied lessons held, and the digest gets one line saying so.
   - `reflect` is not skipped for a brief's MODEL CALLS line: its measurement only reads, and its review is the model call Close exists for. The signals are yours to fold in here unless a flow improver you spawned is running; leaving them to one that does not exist drops them.

## Where this differs from Orca, and why

Orca's `orchestration` skill is the default; these are the places a program overrides it on purpose.

| Orca says | This skill does | Why |
|---|---|---|
| Start the full independent wave before waiting | Ticket workers start at a cap of 1 that grows by one per landing proven green on main and halves on red | The pilot fixes the brief, unit size and VERIFY before they are copied; past what main CI and the land lanes absorb, more workers only grow the landing backlog (`references/landing.md`: stop starting, start finishing) |
| Pass `--model` only when the user named one | `--model` is `orch model worker` (`orchestrate.models`), or the program note's when the human named one | The pilot proves that model reaches its first `orca orchestration` call and `orch land` without a permission prompt, and the note keeps a resumed lead on the same model; the user's agent default can change under a running program (`/model` changes it globally) |
| Share the current workspace; a new worktree only on a real checkout conflict | One `new-child` worktree per ticket; `current` only for a read-only helper | Each ticket is its own branch and PR landing in parallel, stacked or on `origin/main`; a shared checkout would mix their branches. `new-child` records your worktree as the card's Orca parent, so the sidebar shows the program's cards under you. `new-top-level` drops that lineage and is used only where the brief names it (its LINEAGE row, `references/brief.md`); when Orca refuses `new-child`, stop and report it rather than retry as `new-top-level` (core rule 5) |
| The lead's turn ends only on its report to the user | `orch wait` runs in the background and the turn ends while it waits | A program outlives any one turn: the wait wakes you on worker_done, escalation or question and acks heartbeat-only batches, and under `/goal` it defers the Stop hook's check. Orca's end condition still closes the program (Close) |
| `worker_done` body is three sentences | The brief's REPORT asks for the PR URL, merge commit, reviewers, the VERIFY output seen, the main-CI run and the findings with their proposed class | That body is the landing's evidence and the only channel for what a worker must not write outside its worktree; the lead records it |
| `terminal send` only for prompts that need no task state or inbox | One exception: after the content goes through `orchestration send --to dispatch:<id>`, or `orchestration reply --id <msg>` for a question (the reply is what closes it on the dashboard), wake a worker whose turn ended before its Dispatch settled (a settled one gets a new Dispatch, never a wake) by `references/waking.md`, which picks `SendMessage` or the one-line typed nudge | `send` does not wake an idle agent; a worker sat 80 min on an answered blocker. The content stays in Orca's tracked mail; a worker without a terminal gets Orca's recovery instead. A typed nudge counts as taken over: `worker-release` refuses it from then on, and it closes through the `TAKEN OVER` self-check |

## Traps seen in real runs

The lead's rows of SKILL.md "Traps seen in real runs".

| Trap | Instead |
|---|---|
| A lead granting each merge | Workers land through `orch land`. The lead became the slowest lane |
| "Whoever is ready lands next" | Dependencies in Orca, and the land order for the exclusive lane. A dependency root starved for 5h behind newer PRs |
| One merge baton under strict up-to-date branches | A parallel normal lane with strict off. Every landing had pushed every other PR behind for another 30–40 min of CI |
| Landing a dependency chain one PR at a time (rebase + CI between each) | Stack it; the top's `land` merges the chain in one `merge-async` |
| Workers idling for hours "waiting for the merge slot" with nothing to do | `land --wait-minutes` in the background. `status` STALE lines and backlog hours make the wait visible and actionable |
| A worker calling `gh stack merge` or `gh api … merge-async` itself and the classifier refusing it as "Merge Without Review" | Merges happen only inside `orch land`, which is the review gate and the allowed command |
| Reverting every red main by reflex, or the lead debugging it | The main guardian: flake check first, then hotfix or revert by the rule in `references/roles.md` |
| Cards named by Orca's automatic title, one unrelated to the ticket | `--display-name "<ID> <title>"` on every start; a terminal rename does not stick |
| A hand-written `worker-start` spec starting with `/goal` | Start the spec with the ticket ID; Orca already delivers it as the worker's task. The spec `skills-sync card` composes from a brief file keeps the brief's `/goal` line on purpose, and a card from `orca worktree create` is the opposite: `/goal` plus its brief (`dispatch-card` §2) |
| A worker shows `live` but has done nothing for many minutes | It may be sitting on a permission prompt (`status` lists `idle-waiting`): `worker-read --dispatch <id> --source terminal`. Answer it inside the approved scope as for a `STUCK` line (SKILL.md Drain); outside it, put it in the digest for the human. Waiting output does not prove the agent stopped, so do not stop or retry it |
| A worker that sent a blocker as a status and ended its turn sat 80 min after your `send` answered it | A question (a worker's `ask`, a `/goal` card's `--type question`) is answered with `orca orchestration reply --id <msg>`; a worker waiting in `ask` gets it at once and needs no nudge. Anything else, and a reply to a card whose turn ended: `send` does not wake an idle agent. Send the answer with `orca orchestration send --to dispatch:<id>` (to a card, the reply is that send) so Orca tracks it, then, only for an attempt that has not settled (a settled one gets a new Dispatch), wake it by `references/waking.md`. After a typed wake, text left in its input box needs Enter alone (`--text '' --enter`), not the text again, and that terminal later closes through its `TAKEN OVER` self-check, not `worker-release`. Never put the content itself in `terminal send` or `SendMessage`: Orca keeps no record of it, and a message is not the user's word. A worker with no terminal (terminal verbs refuse its handle) follows Orca's recovery instead: a transcript (`worker-read --source transcript`) whose last turn sent no `worker_done` is Orca's proof it stopped, so read `orca skills get orchestration --reference references/recovery-and-cleanup.md` and choose `worker-stop` or `worker-abandon` |
| A handoff prompt that retypes the rules | The note is the handoff; the prompt is only the lines in "Resume (handoff)" |
| Follow-ups spawned the moment they are filed | Park them; `status` shows derived tickets per predicate item |
| Parallel CI jobs named `1/3 2/3 3/3` | Name jobs by what they check (typecheck, lint, unit, db, api…) |
| Several cards running docker compose stacks and image builds at once; the machine and the Orca UI crawled | Heavy local runs go through `orch heavy`, machine-wide slots: a quarter of the CPUs, at least 2 (`landing.heavy_slots` or `orchestrate.heavy_slots`) |
| Finished setup terminals and landed cards left open (50 terminals; 8 cards after one compaction dropped the step) | `skills-sync close-setup` on every new card; act on the `CLOSE OUT` lines in the turn a worker reports done, and on the `SETTLED` and `TAKEN OVER` lines every wake prints |
| A worker that finished but had no capability token to send `worker_done` stays `active`, and no sweep line names it | Ask it the `TAKEN OVER` self-check; its answer is its REPORT, and you close it out |
| A shared state file overwritten in place and left empty | Append-only ledger; anything else is written to a temp file and renamed |
| Typing `/model` into a worker terminal | Pass `--model` to `worker-start`; `/model` changes the global setting. A session patrol's `M` shows as off its role's model is restarted by its owner with `claude --resume <id> --model <alias>` |
| A check needs a secret the worker's session did not inherit from the environment | The worker writes a script that reads the value from the environment and prints only the result, never the value; the lead reads it, runs it in its own terminal and sends the output back. Only for a value that is missing: a check a guard refused follows SKILL.md "Refused acts" |
| A worker that has run for hours keeps hitting model API 5xx errors or timeouts; its context is too large, and `/compact` is as heavy | Replace it, do not retry it in place: the layer above reads its worktree (branch, commits, what is unpushed), writes a fresh brief with what is done and what is left, starts a new worker on that card, and releases the old one |

## Resume (handoff)

The new lead's whole prompt is two lines, `/goal orchestrate resume <slug>` and `ROLE: lead <slug>`; the second binds the program to that session for the reorient hook. Start it with the `--model` that `orch model lead` prints. A session started with `claude --agent agent-skills:lead --name lead:<slug>` needs only the first. On resume:

1. Read the program note.
2. `orca orchestration run-use --id <run>`.
3. Make `program.json` match the note: `orch set <slug> merge_policy|ceiling|deadline|predicate|exclusive_paths …` for any difference. The note wins.
4. `orch status`.
5. Stop any inbox watcher the program ran before (a Monitor, a script), start the one `orch wait`, and continue at Drain.

After a restart of the session, Orca or the machine, or an automatic compaction, run `agent-skills:reboot` before anything else. A lead started as a dispatched worker that lost its Dispatch in the restart must not `run-use` its coordinator's Run (step 2): `reboot` sends it to `orca orchestration run-create`, then `orch set <slug> run <the new Run>`, which takes only the Run this terminal is bound to and drops `lead_dispatch`. Never edit `program.json` by hand for it.

Whenever the note's policy, ceiling, deadline, predicate or exclusive paths change mid-run, mirror them with `orch set` in the same turn. Workers report to the Run inbox, not to a session name, so nothing needs re-pointing. The old lead ends only after the new one has printed `status`.
