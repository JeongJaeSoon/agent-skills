# Dashboard: live program progress without spending tokens

`scripts/dash.py` is a local, stdlib-only page for every program under `$PROGRAMS_HOME`, and for every Orca session on the machine (the fleet view, below). It reads the same sources as `orch status` (the ledger, the tracker, GitHub and Orca) and spends no model tokens. Collecting data is deterministic Python. A model is involved only if you add the optional annotator described at the end.

## Start it

`orch init` and `orch status` run `orch-dash ensure`, so an orchestrator or lead never starts it by hand. `ensure` asks `/api/health` on the port: this store's server running this code answers and nothing happens; one running older code (a plugin update) is stopped through the pid it reported and started again; a port held by another store or another program is reported, never killed. The port stays where the human opened it: without `--port`, `ensure` and `serve` use `$ORCH_DASH_PORT`, else the port this store last served on (`<store>/.dash.json`), else 4780, so a restart after a merge or a reboot keeps the bookmarked URL. `ensure --port P` while this store's server answers on another port stops it there and starts it on P, since the store lock would make a second server exit. A running server re-hashes its code (every non-test script beside `dash.py`, the two it imports from elsewhere, and the page assets) every 30 s; once the code on disk differs from what it runs (a merge landed after it started), `/api/health` reports `stale` and the page shows a banner with the `ensure` command that restarts it. `stale` is also true while the fast loop has not finished a round for 5 minutes (a call that never returns), and under launchd the server exits by itself so launchd starts it again once the silence reaches 15 minutes (`ensure` restarts it at 5). Compare questions to GitHub for the ledger gaps are asked before the program lock is taken, never under it. The sidebar foot shows the running code version and, in a git checkout, its commit. The `orchestrate` wordmark at the top left links home (`#/fleet/overview`); it is the only home link, so the tree has no Fleet row of its own. `serve` holds a lock on `<store>/.dash.lock`, so a second server on the same store exits; its log is `<store>/.dash.log`.

```sh
orch-dash ensure [--port P]
orch-dash install-agent [--port P]   # legacy macOS LaunchAgent; setup does not use it. Prefer `skills-sync setup enable orch-dash` (an Orca automation running `ensure` every 10 minutes)
orch-dash serve [--port P] [--interval 60] [--host 127.0.0.1]
orch-dash collect <slug>   # one collect, prints a one-line summary
orch-dash demo [--port 4780] [--live] [--no-serve]   # fixture programs and an invented fleet, no network
```

On macOS, `install-agent`, run from the git checkout sessions load (a worktree or the plugin cache is refused, since it goes away), writes `~/Library/LaunchAgents/<label>.plist` (`$ORCH_DASH_LABEL`, default `io.github.jeongjaesoon.orch-dash`) and loads it: `serve` from that checkout with `RunAtLoad`, `KeepAlive` and a 30 s `ThrottleInterval`, the PATH of the `python3`, `git`, `gh` and `orca` found at install, and `$PROGRAMS_HOME` when set. Running it again changes nothing that is in place. While that agent is loaded and serves this store, launchd is the only manager and `ensure` never starts a server itself: it stops this store's servers launchd did not start (identified through their health answer, as above) and runs `launchctl kickstart`, with `-k` when launchd's own server is stale or silent. The port is the plist's. A server launchd starts waits on a held store lock instead of exiting, so a leftover server hands over the moment it goes, and once the code on disk has differed from what it runs on two checks in a row, and `import dash` of it succeeds, it exits so launchd starts the new code within about a minute; code that does not import leaves the old server up with its stale banner. Without a loaded agent (Linux, or after `uninstall-agent`), `ensure` behaves as above. Its log is `<store>/.dash.log` too.

`serve` collects in the background at three rates:

| Source | How often |
|---|---|
| Tracker and GitHub | Every `dashboard.github_every_s` seconds (default 300, from 60 to 86400, in `~/.claude/agent-skills.json`; without the key the server logs one warning and uses 300), and at once when a `landed` or `main_green` row is new in a ledger or `POST /api/refresh` arrives. `--interval` no longer sets it. These use the network and have rate limits |
| Stages (tracker tree) | With the line above, at most 24 tracker calls each time |
| Orca (`worker-list`, `task-list`, `run-show`) | Every 20 s |
| Ledger | Checked every 3 s; re-collected when it changes, and at least every 30 s |

A closed program (its `predicate_verified` is current), or a quiet one (no ledger event for 3 days, the line at which the sidebar folds it away), keeps only the ledger check. Its tracker, GitHub and Orca sections stay as last collected, and a landing, a predicate edit, an admitted follow-up or any other new ledger event reopens it. Most programs on a machine are quiet: polling them every 20 s was most of the collector's Orca calls.

The page polls `/api/<slug>/state` every 5 s with `If-None-Match`, so a poll with nothing new gets a 304 and no body. Keep `--host` at 127.0.0.1: the page shows PR titles and worker paths. Every `/api/` read and write answers only a loopback `Host` and `Origin`, so a reverse proxy that reaches the dashboard from another name must rewrite both and do its own authentication. The page has no fixed address: the Brief's dashboard links open and read under whatever address it was loaded from.

Each program's files are in `<program>/dashboard/`:

| File | Contents |
|---|---|
| `state.json` | The page's data, written atomically |
| `history.jsonl` | One row per change in the charted values; rebuilt from the ledger once `orch backfill` puts landings before its first row |
| `notes.jsonl` | Notes (see below) |
| `pr_rows.json` | The last GitHub rows, so the land order can re-rank on a ledger-only refresh |
| `usage-cache.json` | Byte offsets for reading transcripts incrementally, and each session's last state |
| `tree.json` | The tracker's parent/child tree as crawled so far (the stage bars) |

### When a source fails

A failing source never blanks the page:

- Its error is shown.
- The last good section stays on screen.
- Its timestamp stays at the time of its last success.

## Fleet: every session on this machine

The first screen (`#/fleet/overview`) is not a program. It is every Orca worktree on this machine, arranged as the orchestrator above orchestrations above tasks, with the sessions you opened yourself under the orchestrator too. Program pages stay one click away in the sidebar. `fleet.py` collects it inside the same `serve` process, reads only local CLIs (`orca`, `gh`, `git`), and never calls a model.

### Where it comes from

| What | Source | How often |
|---|---|---|
| Sessions, agents, terminals, orchestration mail | `orca worktree ps`, `orca terminal list`, `orca orchestration inbox --limit 2000` (read without consuming; every message Orca keeps, heartbeats included, so no unanswered question falls out of the window) | Every 10 s while a page is open (it polled in the last 5 min), every 60 s otherwise; opening the page, and every action on it (answer, approve, send, dismiss), refreshes at once, and the page fetches the result about 1.5 s later instead of at its next 5 s poll |
| Runs, workers, tasks, decision gates | `orca orchestration run-list`, `worker-list`, `task-list`, `gate-list` | Every 120 s, and at once when the page is opened after 5 min away. A Run whose workers and tasks have all settled, with no open gate and no orchestrator or lead terminal on screen, is read again only every 15 min (`SETTLED_EVERY`): nothing can move it |
| Which PR a session's branch has | One GraphQL query per 40 branches (`associatedPullRequests`); a branch without an open PR (none yet, or the one it had was merged or closed) is asked again after 10 min | With the PR tick |
| Every PR of mine, in any repository | A GraphQL search (up to 3 pages of 100) for the open PRs you authored and those merged in the last 24 h, returning only each PR's key and updated time: probe fields on a hundred search nodes time out. A PR is on the page whether or not a live worktree has its branch, so a PR whose worker was released stays, and a new one appears on the next tick instead of after branch discovery's 10 min. A PR the search saw updated is probed on that tick; otherwise it keeps its tier below | Every 30 s while a page is open, every 90 s otherwise. A failed search keeps the last list |
| PR reviews, review threads, requested reviewers, CI | A cheap probe (state, head, updated time, CI rollup, merge state, review decision, CodeRabbit's commit status) for every PR that is due, then a full read only for the PRs whose probe changed | With the PR tick, 25 PRs to a query (50 took over 10 s and at times timed out); a chunk that fails costs only its own PRs. While a page is open every open PR a session owns is probed at least every 90 s. With no page open a PR is due every 90 s while hot (CI running, approved, its session working, or updated in the last 2 h), 5 min when warm (updated in the last day) and 15 min when cold; once a day after it is merged or closed. Opening the page after 5 min away probes every open PR a session owns at once, and a session whose phase changes (a turn ends, a worker starts) has its PRs probed on that same tick. A probe that saw a change is recorded only once the full read lands, so a failed read is retried on the next probe. Each query's `rateLimit` is kept; below 300 points left, the regular PR tick runs at most once per 15 min until the hour resets (a phase change or opening the page still probes) |

A PR that has not changed costs one alias in one probe query; only a changed PR is read in full. Avatars are downloaded once per reviewer, only from `avatars.githubusercontent.com`, into the state directory; the page never loads an image from outside this server. The page does not ask for a team reviewer's avatar (there is none), and one that failed to load is not asked for again until the page is reloaded.

The hierarchy comes from Orca's own records and the roles sessions declared. The root is `root_worktree` from the config; without one, the worktree of the one live Claude Code session declared orchestrator (`ROLE: orchestrator` recorded by `hooks/reorient.py`, or `--name orchestrator`), matched by its working directory and, where folder contexts share that directory, by its session name; without that, the worktree whose terminal coordinates the newest Run among those whose bound session (Orca's coordinator) no other on-screen bound session dispatched and no session declared a lead (a lead started with `worker-start` opens a newer Run of its own, so the newest Run alone is not the top level; without the declared roles, a top level with no Run of its own would lose the root to a lead's newer Run, and that lead would leave the Brief). A Run's bound session's worktree is an orchestration, under the session whose Run dispatched it, else under its Orca parent, else under the root. A worktree whose session declared a lead (`ROLE: lead <slug>` or `--name lead:<slug>`) is an orchestration too, even with no Run. A dispatched worker's worktree is a task under its orchestrator or lead. Anything else is standalone, under its Orca parent (`parentWorktreeId`, which a lead sets on workers it made with `orca worktree create`) when that parent is on screen, else under the root. A parent loop, from sessions that dispatched each other or from Orca parents, is cut loose onto the root, so the tree never loops. On screen an orchestration reads as a **lead**: the sidebar sets its name in bold with the number of sessions under it in grey beside it, and the Kind column and session page say `lead`. A task, or a standalone under a lead, reads as `worker`; the orchestrator and a standalone under the root keep their kind. Only the label changes: `kind` in `state.json` stays as above. Nothing is written to Orca to build it (see adoption below).

Rows the board lacks are derived (`--no-fill` turns that off): each lead session whose terminal no board lead holds becomes a lead row, the cards under it its `└` rows and the root's own cards rows of their own (a standalone card only when Orca records the orchestrator as its parent, or with a report, a PR or a dispatch, so a resident folder such as an automations runner is not one: the root the collector hangs an unparented worktree under is no evidence), each with its current PR, a status from the session's phase (working 🔄 `작업 중`, idle 🔄 `턴 종료`, waiting 🙋 `확인 대기`, the owner's, open or offline ⏸️) and the later of its last activity and its report file's change as the confirmed time, so a quiet one shows its age. The next step is the report file's newest milestone (its `다음:`/`Next:`/`次:` line, else its first line) when the session's brief, the path in its Orca comment, names that file on its REPORT line or says "this note"; when the REPORT line sends to `run:<id>` and names no file, it is the newest `status`, `worker_done`, `merge_ready` or untyped message the card's own terminal (its handle, or its pane as `sender_pane_key`) sent to that Run or its coordinator's terminal, read from Orca's inbox (heartbeats, questions, escalations and gates are left out); a session whose comment names no brief (a `/goal` card, a lead) gets the same from the mail it sent to a Run its parent session coordinates, never another Run, where the mail may be an order sent down; otherwise it is the phase's. Each subagent a session started and was not seen to stop is a row too (see Subagents below): a `└` row under the lead its session's row hangs under (a lead's own, or a card's under that lead, a session with no row of its own taking the nearest session above it that has one), else a row of its own (the orchestrator's own subagents, a top-level card's). - **Data flow.** The registry in `scripts/registry.py` drawn as producers, stores and consumers. Each store is one file pattern under a state root, an outside source (Orca, GitHub, the tracker, transcripts, the card reports) or, from the database PRs on, a `db:` table, with the facts it holds and each fact's role there: canonical (the one place that changes it), derived, cache, log, backup, lock, hand file or removed. It also names the functions allowed to write it and who reads it. Values come from stat only: path, last change, size, entry count for a pattern, and for a `.jsonl` its line count (counted from where the last count ended while the file only grows) and its last row's `ev`/`kind`. Each store is present, off (the config key that turns its writer on is missing), not yet written, or error (unreadable, or a directory where a file belongs); a consumer with no input present is starved, labelled with the worst of its inputs' states. A store older than its interval is stale. Below the drawing: the facts with two canonical stores (the known ones with the PR that removes them), the files under the state roots no store names (program directories count as the lead's own files; of the programs home only its `_` directories are walked, and the directories a shared-state pattern names when the two share one directory), the report files the sessions name, and the whole registry as a table. Locks and backups are in the table only. `GET /api/fleet/flow`, rebuilt at most every 30 s.

  `test_registry.py` holds the code to the registry: every fact has one canonical store (`DUAL_CANONICAL` lists today's exceptions with the PR that removes each), and an AST scan of every script finds each write (`write_atomic`, `append_line`, `open` for writing, `write_text`, renames and copies, and functions that pass a path through to one of these) and checks that its file is registered and its function is one of the store's writers. A change that adds a state file, or writes one from a new function, adds or edits its `Store` in the same PR. Writes outside agent-skills' data (a launch agent plist, a report to `--out`, the trash) are listed in `OUTSIDE` with the reason. `python3 registry.py check` prints the same violations; `registry.py writes` lists every write site the scan found.

### Units

`GET /api/fleet/units` (`scripts/units.py`) joins what the Brief and Sessions each draw: one **unit** per session, per board row no session carries, per started subagent, and per open PR that no single session owns. It is a join of `rowstate.inputs()` and keeps nothing: no store, no cache, no setting. Each request runs `units.py` in a child process over the same render as the Brief (`--no-refresh` semantics: it reads `state.json`, never collects), so a slow render times out there and not in the server. `orch brief render` and the Brief's status marks are not touched by it.

A unit carries `id` (`card:<worktree>`, `row:<id>`, `agent:<id>`, `pr:<key>`), `kind` (`lead` for the orchestrator and a lead, `worker`, `solo`, `subagent`, `item`, `pr`), `session`, `rows[]`, `prs[]`, `tickets[]`, `state`, `owner_turn`, `dirty`, `pr_unknown` and its `group`. `groups[]` lists every unit in exactly one group: under its lead (`by: lead`), else under the program its board row names (`by: project`), else in `Solo`; the orchestrator heads a `root` group and a PR no session owns sits in the last one. `group.parent_source` says how the collector found the session's parent: the Run its Dispatch belongs to (`dispatch`), Orca's own parent field (`orca`), or neither (`fallback`, the root filled in).

- **State.** Only `rowstate.judged()` decides it. A session the Brief gave no row (it is offline, its PR is on a board row, its dispatch finished, or it is not a card) gets a synthetic row, the dict `fleet_rows` writes for a card, and goes through the same `judged()`; its `rows[].via` is `synthetic`. No status is worked out from a phase or a PR here. A unit with several rows takes the one that needs attention most (`rowstate.rank`).
- **PRs.** A PR claimed by two or more sessions (`state.prs[].candidates`) is linked to none of them: it is listed in `link_unknown`, each claimant shows `PR link unknown`, and the PR is its own `pr:<key>` unit unless a stored board row names it. A row the collector wrote is no claim; a board row's own `--pr` is. An older collector without `candidates` falls back to the one session it recorded, and `unknown` names `candidates`.
- **Tickets.** Computed here once, so the screens do not each scrape ids: the card's own tracker links (`refs`), then ids in the session name, branch, brief row titles and task title. `url` is `dashboard.ticket_url` plus the id, else the card's link, else null.
- **`dirty`** is the janitor's answer (`rowstate.card_dirty`, from its latest plan, nothing read again): uncommitted changes in the worktree, where a tree holding only regenerated copies is `false`. `null` is unknown, never "clean": the card is one the janitor protects before it reaches `git status` (a worker with a live turn, a lead whose pid is unconfirmed), has no row in the plan, or the plan is older than `DIRTY_PLAN_MAX_MIN`. A card the janitor sends to a person (사람 결정) is treated the same way, as unknown. `unknown` in the response names the inputs that could not be read.
- **Not here yet.** A disconnected-session verdict, the inbox rule, the canvas and moving a unit under another lead are later steps; this response has no setting for them.

The **Sessions** screen is the preset of these columns: name (tree), kind, phase and model, ticket, PR, Brief, the owner's turn (🙋 beside the Needs you count), activity and project. It keeps its tree, the lead folds, the dimmed subagent rows and the Finished line; ticket, PR and the owner's turn are read from the unit of each session, and the Brief column still shows the Brief's own marks.

### Inbox types

| Type | Raised when |
|---|---|
| `prompt` | A `permission` item whose terminal shows, right now, the permission dialog `hooks/permission.py` recorded: it carries Approve, Deny and Open terminal (below) |
| `permission` | An agent sits on a permission or input prompt (Orca reports it as waiting) |
| `question` | A `question`, `escalation` or `decision_gate` message to an orchestrator or lead that no one has replied to. It stays after the orchestrator or lead acks it (its inbox loop acks at once, before you have answered) until a message in its thread comes from someone else, or for a day; an unread one stays until it is answered. Mail from a worker whose dispatch has settled (completed, failed or abandoned; the dispatch is read from the payload or a `dispatch:` sender) goes at once; workers are listed per Run with `worker-list --run`, since without it the list is scoped to the Run bound to the terminal that started the server. Mail whose sender later sent the same recipient a `status` or `worker_done` outside the mail's thread goes too: the sender has moved past it (a heartbeat, a report inside the thread or a newer question does not count) |
| `decision` | A decision the orchestrator or lead registered with `orch decide add` and has not closed (below) |
| `approval` | A pending Orca decision gate, or a finished turn that ends asking for a decision |
| `login`, `run_command`, `verify_failed`, `verify_ok` | A finished turn that ends asking you to log in, to run something yourself, or reports a verification that failed or passed |
| `changes_requested`, `review_comment_received`, `ci_failed`, `approval_stale`, `ready_to_merge` | A PR owned by a session has a change request, unresolved review threads from a person (bots are left out unless `bots_in_inbox`), failing CI, only approvals on an older commit, or a current approval with passing CI |
| `sync_stalled`, `reload_pending` | Skill sync reported failure or went quiet for two intervals, or a reload the dashboard's retries could not send to an idle session (below) |
| `owner_todo` | An open item of the owner's now-list (`orch board now`), the same set the Brief's 📅 list shows. Its key is the board item's id, so `orch board done` closes it and the next read drops it |
| `selfcheck` | The dashboard's own state disagrees with a fresh read of Orca and GitHub (below) |
| anything else | Added by the orchestrator with `orch-dash inbox add` |

Needs you is sorted by rank, newest first within a rank (`NEEDS_RANK` and `needs_order` in `scripts/fleet.py`). Newest compares the moment, not the text: skills-sync writes `+0900` where the rest write `Z`.

| Rank | Types |
|---|---|
| 0, only you can settle it | `decision`, `approval`, `permission`, `prompt`, `question`, `login`, `run_command` |
| 1, a merge call waiting on you | `ready_to_merge` |
| 2, the rest | every other type |
| 3, held | a PR item whose PR a held board item (`orch board later`) or a to-do (`orch board todo`) names in its title by its full `owner/repo#N`, or by a bare `#N` only one PR in the collector's list has. It shows `held` (`to-do` for a to-do) and the item's trigger, and returns to its own rank when the item is dropped or closed, when its `--due` or the date in its trigger (`M/D` or `YYYY-MM-DD`, optional `HH:MM`, local time) comes, or, with no date, when every PR its trigger names has merged; for a to-do, whichever of these comes first |

The turn-based types read only the last lines of the agent's final message that Orca already reports, with fixed patterns, so they are a hint, not a verdict. Items backed by a live condition (a waiting prompt, unanswered mail, an open decision, a pending gate, a PR's state) disappear when it clears; added items stay until dismissed or resolved, or for 7 days after they were added (`EXTERNAL_KEEP_DAYS` in `scripts/fleet.py`; an `inbox_aged_out` event on the timeline marks the day one leaves); `orch-dash inbox list` prints every unresolved one, older ones included. A turn-based item goes when its agent's pane gets a later prompt or starts a later turn (someone already replied there), when the same agent finishes a later turn (what it asked for was dealt with, or the new turn raises it again), when Orca no longer lists its worktree, when its session has had no agent to answer it for 10 minutes (counted only in reads that found some agent, as an empty read is more likely a bad one), or when every PR its message names (`owner/repo#n` or a PR URL; a bare `#n` may be a step number and names none) is merged or closed in the PR cache (a PR the cache does not know keeps it); each such close is an `item_resolved` event on the timeline naming the rule (`answered`, `superseded`, `session_gone`, `agent_gone`, `prs_closed`). A prompt in another pane of the same session does not close it. An `approval`, `question`, `login`, `run_command` or `verify_failed` item raised before the session's latest prompt is **missed**: the inbox pins it to the top with a red edge, because typing the next prompt usually means the question above it went unanswered.

A session's **badge** is the number of Needs you items on it, the same list its session page shows. The badges plus the items that belong to no session (sync health, items added without a session) are exactly the Inbox count, and every item is a live condition (or an open turn-based item), so the two never disagree. Nothing local such as a "last opened" mark hides an item from the count: an item leaves only when what it points at settles, it is answered, or it is dismissed; the human never has to clear what reality already settled. A reload skills-sync could not send is retried before it is yours. skills-sync retries only every 15 minutes, so after each collect the dashboard sends the reload again itself, through skills-sync's own `broadcast --only` (same lock and idle checks), to each pending terminal whose session is idle, at most once every 2 minutes per terminal. A terminal that stays busy is not retried and gets the reload once it is idle, so it is nobody's to fix. Only when an idle terminal refuses `reload_alert_tries` retries in a row (config, default 3; the count starts over when the collector starts) does the reload become a `reload_pending` item, on the session of the terminal it could not reach and titled with that terminal; one for a terminal Orca no longer lists is dropped. Once it lands, skills-sync takes it out of `reload-pending.json`, the item goes, and the timeline gets an `item_resolved` line (`reload_delivered`, or `reload_dropped` when the terminal is gone). Orca's own per-worktree unread flag is a yes/no without a count, so it is not used.

### Self-check

The server checks its own output on the fleet loop: every 5 minutes `scripts/selfcheck.py` reads Orca's worktrees, terminals and inbox, GitHub's state of every PR the page shows open, and a search for every open PR of mine, and compares them with the state it serves. A difference counts only when a second read 90 s later still shows it, because the collector trails Orca by up to one tick. What counts becomes one `selfcheck` item per class, with no session, listing up to ten subjects; the item's key comes from the subjects it names, so a lasting mismatch stays one item and a new set of subjects is a new one. It goes once a read no longer finds it. The check raises items and nothing else: it never changes the state it checks.

| Class | Counted when |
|---|---|
| `session_missing`, `session_ghost` | A worktree Orca lists (by the collector's own rule for main worktrees) is not a session, or a session's worktree is archived or gone. An empty worktree list is taken for a bad read |
| `tree_parent` | A session's parent is not in the list, the root has a parent, or following parents never reaches the root |
| `pr_state` | A PR shown open (a row or a PR item) is merged or closed on GitHub, and the collector probed it after the change or the change is older than the slowest probe tier plus 90 s |
| `pr_missing` | An open PR of mine that a fresh search returns is not on the page, and it was opened more than one PR tick plus 90 s ago |
| `pr_stale` | A PR shown open has an older last update than GitHub's, and GitHub's is older than one PR tick plus 90 s (the slowest probe tier plus 90 s for a PR that is not mine) |
| `item_answered` | A turn item's pane has started a later turn, or finished one with a different last message |
| `mail_answered` | A question mail item has a reply in its thread |
| `prompt_gone` | A `permission` item's agent is no longer waiting |
| `item_session_gone` | An item names a session that is not in the list |
| `activity_stale` | A session's shown last activity is more than 5 minutes behind its worktree's or agents' own times up to when the state was made |
| `item_text` | An item's title is empty or prints `None`, `null`, `undefined` or `NaN` |

What only the browser shows (the order of the Needs you card, a page still running old code, a failed avatar) is not in this check.

### PR events for the rest of the platform

Every change a full read finds is appended to `events.jsonl` in the state directory (the timeline's file), one JSON line (under 4 KiB, one write) per event, with `kind` `pr_<event>`: `{at, kind, session, pr, actor, url, text, id, repo, number, owner, owner_kind, checks, head}`. `<event>` is one of `review_comment`, `changes_requested`, `approved`, `review_requested`, `head_pushed`, `approval_stale`, `checks_failed`, `checks_recovered`, `merged`, `closed`; readers ignore kinds they don't know. `pr` is the key `repo#number`. `owner` is the live dispatch that owns the PR's session (`owner_kind: dispatch`), or the session's agent terminal (`terminal`, or `human_session` for a standalone session). The file rotates to `events.jsonl.1` past 5 MB. The dashboard itself only displays these; whether a session is told about them is up to the orchestrator. Before the single-source move these rows were also written to `pr-events.jsonl`; that file is now a read-only archive, and `orch-dash migrate-inputs --apply` makes it so.

### Decisions the orchestrator or lead waits on you for

A decision the orchestrator or lead reaches in its own analysis, or hears from a subagent, never becomes Orca mail. The orchestrator or lead registers it with `orch decide` (`scripts/prog.py`, stored in the `decision` table of `agent-skills.db` in the state directory through `scripts/store.py`, masked on write):

```sh
orch decide add --title "Export format for the first release" --body-file /tmp/why.md \
  --option "CSV::finance opens it in a spreadsheet" --option "JSON::one format for both" --recommend 1 [--link URL] \
  --if-no-answer CSV --reason owner-asked   # prints d7; the owner-ask gate (owner-ask-gate.md) refuses it without these
orch decide list
orch decide answer d7 --quote-file /tmp/words.md   # answered: the words as given, the time, this session; prints the line to quote
orch decide answer --title "Ship the beta" --quote "…"   # an order nobody asked for: added and closed at once
orch decide show d7                  # that line again, any status
orch decide done d7 --answer CSV     # closed with no quote to keep
orch decide drop d7                  # no longer needed
orch decide keep d7                  # checked, still stands: sets checked_at
```

Owner orders are two more tables in the same file, added by `orch order setup` (a recorded optional step, `5a-order`): `order_` (`oN`, `kind` order or feedback, the text, its source, `--owner-action`, open/done/dropped) and `order_link` (which card, agent, board item, decision or PR carries it; the link outlives the unit). `orch order add|link|done|drop|list|import` is the only writer; `import` takes the numbered lines of a hand list as `kind=feedback` rows once each (a row keeps its line's key, so a second run adds nothing; `import --check` lists the lines not taken yet; the original file, like a session's memory file, is only read). A unit linked with `--stand-in`, such as the temporary to-do an import replaced, is shown but never carries or resolves the order, so a to-do closed as "migrated" proves nothing. `order_.links_complete_at` (set by `orch order links-complete oN`: the receiving session says every unit the order needs is linked; `--undo` and `reopen` clear it) and `order_.reopen_evidence` are what the automatic close reads (below). A real link added after the mark clears it. The brief counts an open order with no link `board.order_unlinked_min` minutes (10) after it was written as `연결 없는 오너 지시`, naming the oldest; with the tables not set up the line is absent. Units made by the tools link themselves to an open order, so nobody types the link: `skills-sync card --order oN` or an `ORDER: oN` row in the brief (the card's prompt then carries a copy of the order's words, and the worktree is linked as `card:<worktree id>`), an `ORDER: oN` line in a subagent's prompt (the subagent hook links `agent:<id>`), `orch board todo|later|doing add --order oN` and `orch decide add --order oN`. An unknown or closed oN stops the card or adds nothing; `orch order reopen oN` opens a closed one and keeps the evidence it was closed on, so tidy does not shut it again until the units' evidence changes. A `kind=feedback` row is not closed on the session's word: `orch order done` needs a real (not `--stand-in`) `pr:` link that `gh` shows merged, and keeps the merge commit in the close event; `orch order drop` needs `--reason`. The orchestrator's `delegate_gate` hook adds a warning, never a block, to a `skills-sync card` or an Agent call that names no order.

Closing by evidence (`order_close.py`, run by tidy after its own closes). An open order is a candidate when its receiving session marked `links-complete`, it is not `--owner-action`, nothing waits on the owner at a card or PR it links (an inbox or human-gate item on the card's session, an open decision from its terminals, an open board item the owner holds that names it; an unreadable inbox or unknown owner login counts as waiting), and every real unit has ended on its source of truth: a PR GitHub shows merged (the collector's detail first; `gh` only for a PR it has not seen), a card whose session is idle with its current PR merged and no step after the merge, a subagent whose last run stopped, a board item that is `done`, a decision that was answered. Not ended: a `--stand-in` link (not a unit), a PR closed without a merge, a dropped board item, a withdrawn decision, an archived or deleted card, a source that could not be read, a session list older than 15 minutes. A `kind=feedback` order also needs a merged `pr:` unit. The evidence is normalized to PR key and merge commit, card id and its PR's merge commit, agent id and run, board id and its close event, decision id; every close by `orch order` writes it into the close event, a Reopen keeps it in `order_.reopen_evidence`, and the order is closed again only when it changes (a Reopen that could not read the units makes the next readable reading the baseline). The write transaction reads the order and the units that live in the DB again before it writes. The first rollout is a shadow: with `orchestrate.order_auto_close` unset (the default; only the JSON value `true` turns it on) tidy writes one `would_close` event per candidate and evidence, closes nothing, and `orch order shadow` sets those candidates against what the sessions did (agree, pending, differs, reopened) and lists orders closed by hand that never were a candidate (missed). The lead turns the key on after 48 hours of shadow with at least one reviewed candidate and no differs or reopened.

A closed decision stays in the table; readers filter on its status. While no `agent-skills.db` exists, decisions live in `decisions.json` under `decisions.lock`, and `orch db import` takes them from there. A DB file that is there and not imported stops `orch decide`, which names `orch db cutover-plan 4a`, and the brief's headline shows `이행 대기: 결정 DB` (docs/orca-migration.md). `keep` changes nothing but `checked_at`; the brief counts an open decision as `오래된 결정` once `board.decision_stale_h` hours (12) passed since the later of `created_at` and `checked_at`, as `등록 터미널 없음` while the terminal that added it is not in the fleet and the relay falls back to the root's writable agent terminal, and as `응답 경로 없음` when the terminal the relay would type into has no running, writable agent or there is none (one added outside Orca always goes to the root).

The item sits on the session whose terminal ran `add` (`$ORCA_TERMINAL_HANDLE`), or on the root. It shows the title, its age, the body's first line, and one button per option, the recommended one with a check; an option's description is its button's tooltip. A line under them shows how to answer in the orchestrator's or lead's terminal instead (`d1: <answer>`, with the recommended option as the answer when there is one). Nothing expands in place. An option button, or the answer box, takes a second click and then answers it through `POST /api/fleet/decide` (same Host, Origin and token guard as the send box). The answer is recorded first: the decision is closed as `done` with that answer, as `orch decide done` would, and leaves Needs you on the next poll. Then `decision <id>: <answer>` goes to that terminal (or the root's agent terminal) through the send box's idle check and log below. A busy orchestrator or lead does not fail the answer: the page says "Recorded; will relay to the orchestrator or lead when it is idle", the decision keeps `delivered: false`, and each later collect retries the line, skipping while the session is working, until it is typed once (a line typed but not confirmed counts as delivered, so it is never sent twice). `orch decide list` prints such answers, the orchestrator's or lead's own `done` stops the retry, and `drop` cancels it. Dismiss only hides the item on this page.

An answer typed into the orchestrator's or lead's terminal closes the decision too. The plugin's `UserPromptSubmit` hook (`hooks/decision.py`) reads each prompt of the terminal whose handle registered the decision, and of no other: a worker's prompt never closes the orchestrator's or lead's decision. It closes one as `done` only when the prompt is unambiguous: its first line starts with the id (`decision d3: yes`, `d3: yes`, `d3 yes`; the rest of the line is the answer), or starts with an option label of two or more characters, not followed by a letter or digit, that exactly one of the terminal's open decisions has (the longest matching label wins). The hook then tells the orchestrator or lead the answer was recorded. Any other prompt closes nothing and only adds a reminder listing that terminal's open decisions (at most five) to the prompt's context. Decisions registered outside Orca have no handle and are never closed this way. The hook is loaded when a session starts: a session that was already running needs `/reload-plugins` or a restart first. Any error exits 0, so a prompt is never blocked.

### Acks: hiding what you have checked

Without it, finished rows only pile up: a ✅ row stays in the stage table long after the owner has looked at it. An ack is the owner's "checked, stop showing it". `scripts/acks.py` keeps them in `acks.jsonl` in the state directory (0600, append-only, `{ev: "ack"|"unack", id, ts}`; the set is the fold of its lines), and the CLI is the record: the orchestrator or lead runs it, and the page's buttons call the same function through `POST /api/fleet/ack` (same Host, Origin and token guard as the send box).

```sh
orch-dash ack stage:release board:lead-a        # a stage row, a brief row
orch-dash ack --done-before 24h [--kind stage|board]...   # all that finished before then
orch-dash unack stage:release                   # show it again
orch-dash acks [--all] [--json]                 # what is acked; --all adds what could be
```

Only what is over can be acked, and the check is the server's, not the page's: a stage row with `done_at` whose rows below are done too, a brief row that is ✅ and, for a head row, every sub-task row under it. A row in progress, waiting on someone, held (a row whose PR closed unmerged is ⏸️ `PR 닫힘`) or asking for a decision is refused with the reason, and the rest of a batch still goes in (the command exits 1 when any id was refused). An ack hides, it does not close: an acked stage row is still in the stage table until its 7 days are up. A `req:` id an older version acked, from the removed owner-request ledger, can only be un-acked. An ack holds only while what it hid is still over: a new open row under an acked group or head row shows it again, and it hides again once that row is done too.

Where it shows: the Stages page (`Ack all N` inside an opened program's finished rows, `Show N acked` above the table), each finished row an `Ack` button (`Unack` while shown); acked rows under an acked group hide with it (the brief reply's `stages` marks each row with `ack`, one of `acked`, `ackable` or null, and `hidden`). On the Brief page each ✅ row of a repository table has its `Ack` at the row's right end, and once acked the row leaves the table with an `Undo` above it until the next inline click. The Finished rows card below lists only the finished rows without an `Ack` in the table (acked ones, `Unack` while shown, ✅ rows folded after 24 h, and those of a table that got no buttons), with `Ack all N` over every one. `orch brief render` leaves acked rows out of its tables (a repository left with no rows loses its table), says `확인함으로 숨긴 행 N` in the headline (acked rows leave before the 24 h fold, so `접음 완료 N` counts only rows not acked), and its `--json` carries `done`: every ackable row with `id`, `label`, `at` and `acked`, and `table_rows`: per repository table in the text, per row, `{id, label, status, session, ack, done}`, `ack` and `done` being the id that row's button posts or null. The page matches each table row to its entry by label (the renderer suffixes a repeated name in one table `·2`, so labels are unique), so a row no entry names gets no button. `list_rows` names the items of the lists under the tables (`owner`, `waiting`, `held`, `moving`), each `{id, label}`; an item with no table row of its own gets its `Done` in its list, and the Open items card leaves out every id a table or list already gave a button.

### Closing what is over, and the stage table

### Shared resources

`orch hold <resource>` records who uses something lanes take turns on (`browser`, `grafana-login`), and `orch release <resource>` gives it back. It has the exclusive lane's shape (`scripts/holds.py`): one file per resource under `$PROGRAMS_HOME/_locks/`, beside the lane locks, and `lock_acquired` / `lock_released` rows in `_locks/holds.jsonl`. `hold` refuses while someone else holds it and names them; holding again refreshes your own. A hold not refreshed within its `--ttl` (120 minutes) belonged to a session that died holding it, and the next reader breaks it and logs `broken after`. `release --force` frees another's hold and logs who did. `orch hold --list` shows every hold and lane lock; the fleet collector lists the same into `state.json` `holds`, each on the session whose terminal handle holds it, and the Sessions page shows them under its table.

### Automations

Every runs cycle the fleet collector also lists Orca automations (`orca automations list`, then `orca automations runs --id` for each) into `state.json` `automations`: name, schedule, enabled, next and last run, and the six newest runs with their status and a masked one-line summary. `sources.automations` says whether the last listing worked. Each row carries `key`, the name in `scripts/automations.py` `AUTOMATIONS` (the list `skills-sync setup` installs from), or `null` for an Orca automation outside it. The page lists only the rows with a key, and the sidebar and header counts use the same rows. The list itself is `GET /api/fleet/jobs` (`jobs.snapshot`): one row for each `AUTOMATIONS` name, once, in that order, joining what Orca says about it (`orca`, the last good listing; `registered: false` when Orca lacks it, `null` for a LaunchAgent or when the listing could not be read), the jobs that run inside it and `record`, a stand-in from the job's own file for when Orca has no run to show. Without `scripts/automations.py` beside the install the answer carries `automations: null` and `error`. A session's own `CronCreate` jobs live in that session and are outside the fleet, as is a LaunchAgent's state.

### Jobs inside an automation

What orch-dash runs on its own clock opens under the `orch-dash` row, from `scripts/jobs.py`. Each job records its run as it runs (`jobs.record()`) into `jobs.json` in the state directory, replaced whole under `jobs.lock`: when it ran, whether it failed and the error (masked, whole), what it did in words, how many it closed, linked or added and when it last did any, and when its own loop runs it next at the latest (a wake-up can run it sooner). Nothing else writes the file, so a job that has not run in this store shows `no record`, never an estimate. `record()` never raises: a record or timeline line it cannot write goes to orch-dash's stderr, and the job and its loop carry on.

| Job | Cadence | Records |
|---|---|---|
| `fleet-tick` (Fleet tick) | every 10 s while a page is open, else 60 s | the Needs you count; a source that failed stays the sources bar's, the tick itself ran |
| `tidy` | after each fleet collect (rides on `fleet-tick`) | items closed (`tidy.py`) |
| `relay` | after each fleet collect (rides on `fleet-tick`) | decision answers relayed and skill reloads sent |
| `selfcheck` | every 5 min, 90 s while a finding waits for its second read | the self-check's Needs you items |
| `skill-usage` | every 15 min | new usage signals |
| `pr-stats` | every 6 h, 1 h after a failure | that the counts refreshed |

Two jobs keep a record of their own, read as the stand-in `record` of their `AUTOMATIONS` row (`sync`, `reap-hard`) and shown only while Orca has no run for it: skills-sync from `sync.json` beside the state directory (its `interval` gives the next run) and reap-hard from its last pass (`reap_hard.read_last()`: closed and kept counts, a failure count or the error that stopped it; its notes are not shown); a record it cannot read is an error on that row only. The session patrol has no schedule: a reap-hard pass starts it, so its row opens under `reap-hard`, from `patrol-verdicts.json` beside the state directory (when the last round ran; a round cut short by its budget is a failure). A failed run of an orch-dash job puts one line on the timeline in the fleet's event format, `job_failed`, when the job starts failing or its error changes, not every run it keeps failing; the record keeps that line's time and the job's row links to the Timeline with it. The line carries the job's key and is cut to fit the 4 KiB event line (`EVENT_TEXT_BYTES`, counted as written, in JSON-escaped UTF-8), so it links back to the Automations page, where the row holds the whole error, two lines until clicked. The row holds the latest error only: once the error changes, a superseded line's cut text is all that is left of it. The launchd jobs write no timeline line from here: a stopped sync is already a Needs you item.

A job's line uses the list's columns: name, how often in short (`10s`, `5m`, `6h`; the sentence above on hover) under Cadence, next and last run, and the result. A job that rides on another (`group` in `dash.JOBS`) folds into that job's row, which names the riders that changed something or failed, counts the rest as `no change` and `no record` apart (`3 more: 2 no change · 1 no record`), and opens to one line each. A run that counted 0 says `no change` with its words in grey under it; one that counted more is bold; the last run that changed anything sits under the result. A job with no record is one grey line with the reason (patrol: no round recorded in this store yet).

Rules applied whenever data is read or drawn have no run, so they are listed apart with the value in force: the 7-day inbox item expiry, the brief's ✅ fold (`board.done_fold_h`) and the stage table's idle fold (`board.stage_idle_d`), and the 7 days a finished stage row stays. `GET /api/fleet/jobs` reads `jobs.json` on every poll rather than through `state.json`, which a tick that fails never rewrites. The code hash that restarts the server also covers `scripts/automations.py`, since the list's names come from it.

### Monitors

In the same cycle the collector lists the background watches into `state.json` `monitors`, without a model and without touching the processes. Live sessions come from Claude Code's `sessions/<pid>.json` under every config dir in use, whose pid and `procStart` must match `ps`: `$CLAUDE_CONFIG_DIR`, `~/.claude` and each Orca profile's (`~/Library/Application Support/orca/claude-profiles/*/home`), since Orca starts every agent with its profile's own `CLAUDE_CONFIG_DIR` and the session registers there only. `ORCH_CLAUDE_HOMES` (paths separated by `:`, globs allowed) replaces that list. The transcript is looked up under the dir the session registered in. The orchestrator and lead roles (`declared_roles`) and Sent read the same sessions. Each session's transcript gives every Bash run with `run_in_background` and every `Monitor`: the start, each event, and the task notification that ended it with its status and exit code. A notification that arrives while a turn runs is written only as a `queue-operation` enqueue line and a `queued_command` attachment, not as a user turn, so all three are read; the first one dates the end. Each tick reads only what was appended since the last one. A task without an end record is `running` only when a shell the session started directly runs exactly its command (the `eval '…'` payload, not a substring) and started within 15 seconds of the task; a foreground run of the same command does not count. Otherwise it is `lost`, because stopping a task from the UI, a Monitor's expiry and a teardown leave no record. A Monitor past the expiry it was given counts as ended. A task that failed or exited non-zero is `dead`. One `killed` or `stopped` was ended on purpose (the UI) and counts as ended; so does one named by a successful `TaskStop`, which writes no notification, only its tool result. A dead task whose notification was written as a user turn or an attachment reached the session's model and is marked `seen`: the page lists it without a ▲. One still only in the queue is unseen. A dead or lost task stays listed for 6 hours, or until the same command starts again in that session; a cleanly ended one is not listed. A transcript that ends in a `continued-in` line is skipped: its session goes on in a new transcript that repeats the tasks it started. `sources.monitors` says whether the last listing worked; its `warning` names a live session whose transcript was found neither under its cwd's directory nor by session id. Commands are masked before they are written, including a URL's password, `-p<pw>`, `--password <pw>` and hyphenated header names. Not collected: tasks inside a subagent, a session's `CronCreate` jobs, and launchd jobs.

### Sent instructions

`orch sent add --to WHO (--text-file F | - | --text T) [--kind K] [--channel HOW] [--repo R] [--subject S]` logs one instruction as it is sent: to another session or card, a subagent, an inbox, Slack or a tracker. Pass the text in a file or on stdin (`-`); `--text` puts it in the process list and in the shell's quoting, so it is only for a short string with nothing secret. The text is kept as sent, one JSON object a line in `<fleet state>/sent/YYYY-MM-DD.jsonl` (UTC day, the file 0600 in a 0700 directory): `ts, from, to, kind, channel, repo, subject, text`. `from` defaults to `$ORCA_TERMINAL_HANDLE`. `kind` is one of `card terminal inbox subagent agent slack tracker other`. The log and Orca's inbox are the sources that outlive the sending session, and the log is the only one for Slack and tracker sends.

What Orca keeps is not logged. A card started with `worker-start`: its spec is the Run's Task, and the page lists each Task of the Runs the collector reads as a `worker` row from its creator to the Task. An `orca orchestration send` or `reply`: the page lists every message of `orca orchestration inbox` but heartbeats, with the channel `orca <type>`, kind `report` for a `worker_done`, `question`, `escalation` or `merge_ready` or a message to a `run:` inbox (up to a coordinator), `inbox` otherwise, and its message, thread and Run ids. The inbox read is the collector's own, the newest 2000 messages, heartbeats included (about a week): an older message is not on the page. When the read came back full, `inbox_since` in the response says where it starts, and `orch sent list` says so on stderr when that falls inside the window asked for. Both are source `orca`. `orch sent add` is for paths outside Orca.

A line typed into a session from the dashboard's send box is written to this log by the page itself (`kind: dashboard`, `from: dashboard`, `to` the session, `channel` the terminal handle), so it needs no `orch sent add`. Before that move such lines were in `sends.jsonl`; `orch-dash migrate-inputs --apply` copies them into the log once and keeps the old file read-only as `sends.archive.jsonl`.

The transcripts are a check, not a source of rows. Each runs cycle the collector reads the transcripts of the live Claude Code sessions (found as for Monitors, read incrementally): an `Agent` call's prompt, a `SendMessage`, and in a Bash command every `orca terminal send --text`, `orca worktree create --prompt` and `orca orchestration send` (`--body`, else `--subject`; heartbeats skipped), parsed with `shlex`. A command shlex cannot split, or a send without its text, is skipped; a text passed as `"$(cat file)"` shows as that, since the file is not read. A row from Orca or a transcript whose text matches a log row within 10 minutes is folded into that row, which then names both sources; a transcript row folds the same way into an Orca message, and a log row an Orca message folds into takes its ids. A transcript send that matches neither is no row: the response counts them in `unrecorded` and the page and `orch sent list` warn "N sends match no log or Orca row", since the sender skipped `orch sent add`. Two Orca messages never fold. When both receivers are Orca addresses of one form (both `dispatch:`, both `run:`, both `term_`) they must be the same; Orca files a send to a Run's coordinator terminal under `run:<id>`, so `term_` and `run:` are not compared. A transcript copy whose text was `"$(cat file)"` does not match and is counted as unrecorded. An ended session's transcript rows leave with it. `GET /api/fleet/sent?days=N` (default 1, 1 to 30) returns at most the newest 3000 rows, each through `mask()` (text, subject, sender, receiver, channel, repository, cwd); a line of the wrong shape in either log is skipped, and any other failure comes back as `{"error"}`; `orch sent list [--days N] [--json]` prints the same. Each poll reads only what the log gained since the last one, and the collector drops transcript rows older than 30 days.

### Sending a line to a session

The session page has a send box for its agent terminal. It is off the network by construction and guarded on every step:

- The server answers only requests whose `Host` (and `Origin`, if any) is this server on 127.0.0.1 or localhost, and POSTs need a per-process token the page fetches from the same server.
- The target must be a connected, writable agent terminal of a session in the current fleet state; a plain shell is never a target.
- One line, at most 2000 characters. The page shows exactly what will be typed and where, and sends only after you confirm.
- The line is typed only if the platform's idle check (`scripts/sync.py` `try_send` at the repository root) finds the session idle at an empty prompt: not busy, no dialog open, nothing typed in the composer. Without that script, or when the check refuses, nothing is typed and the page offers Copy instead.
- "Sent, but the screen does not show it was taken" means the line was typed and Enter pressed. The page says so and does not offer a retry, so nothing is sent twice.
- A line that was typed goes to the `orch sent` log (`kind: dashboard`); every other attempt (refused, failed) is appended to `sends.jsonl` with the text masked.

The send box never answers a dialog: its idle check refuses while one is open.

### The Orca button

A Brief row's session cell has an `Orca` button. It POSTs `/api/fleet/open` with the session's worktree id under the same Host, Origin and token guard, and the server runs `orca terminal switch --terminal <handle>` for that session's agent terminal (else any connected one), looked up at the click. That command moves only the Orca desktop app of the machine the dashboard runs on. Orca's CLI has no switch that moves another device's window from here, and the server cannot tell which device clicked, so the reply never claims the clicking device switched:

- `navigated: true` in Orca's reply: `ok: true`, and the page says it switched in the host's Orca window only.
- `navigated: false`, a refused switch, or a reply without the field: `ok: false`. A reply without `navigated` comes back as `result`, as Orca sent it, with one `warning` line; an unknown outcome is never reported as success.
- Every reply with a terminal carries `copy`, and the page shows the last click's outcome in a note fixed at the bottom right (a table row keeps its height), with a `Copy` button, until its close button; a reply to an earlier click that arrives late does not replace it. The copy is the switch command to type on the other device when the config sets `orca_environment`, else the session's workspace name, terminal handle and worktree path, to find it by hand.

`orca_environment` is the name (or id) the other device saved for this host's Orca server (`orca environment add --name <name>`, listed by `orca environment list` on that device). With it, `copy` is `orca terminal switch --environment <name> --terminal <handle>`, which moves the desktop app of the device it is typed on. It is unset by default, and then the copy is the workspace, handle and path. Each attempt is appended to `sends.jsonl` (`text: "open"`).

### Answering a permission prompt

The human decides; nothing answers a prompt on its own. The plugin's `PermissionRequest` hook (`hooks/permission.py`) writes the tool name and its masked string arguments to `prompts/<terminal handle>.json`, keyed by `$ORCA_TERMINAL_HANDLE`. It prints no decision, so the permission flow is unchanged. `PermissionRequest` rather than the `Notification` hook's `permission_prompt`: the notification fires only after about six seconds without typing and carries only "Claude needs your permission", while `PermissionRequest` fires when the dialog opens and carries the tool input to show and to match.

On each collect, a session Orca reports as waiting whose agent terminal has a record gets its screen read (`orca terminal read --screen`). When the screen ends in a permission dialog (a rule, the request, `Do you want to …?`, numbered options, `Esc to cancel` last) that shows the recorded request (its command, file name, URL host or a string argument, whitespace ignored), the item becomes `prompt` with the command and up to three buttons. A question list, the folder-trust dialog or an unmatched dialog stays a plain `permission` item. When the dialog closes, Orca stops reporting the wait and the item goes.

Approve and Deny take a second click, then POST `/api/fleet/prompt` under the same Host, Origin and token guard as the send box. The server:

- takes the terminal from the prompt record of that session's agent terminal, never from the page;
- under the lock `scripts/sync.py` uses for reloads and the send box, reads the screen twice 1.5 s apart and refuses unless both show the same dialog for the recorded request (only the dialog is compared: the pending tool's bullet above it blinks);
- presses one digit and no Enter: the option labelled exactly `Yes` to approve, `No` to deny. An option that saves a rule or changes the mode (`don't ask again`, `always allow`, `switch to auto mode`) is never chosen; when every Yes is one of those, Approve is not offered and the server refuses, so answer in the terminal (Open terminal switches Orca to it);
- reads the screen again: the dialog gone is success. Still showing means the digit was pressed but not confirmed, and the page does not offer a retry.

Every attempt, refused or not, is appended to `sends.jsonl` (`text: "prompt approve"` and the like, with the digit pressed); an answer is an action, not an instruction, so it is not in the sent log. The hook needs `/reload-plugins` in sessions started before it landed. Dialog shapes were measured on Claude Code 2.1.282; a changed shape makes the item a plain `permission` again rather than a wrong answer.

### Subagents

A subagent is its session's work, so it is never written to the board: the plugin records it. Its `SubagentStart` and `SubagentStop` hook (`hooks/subagent_log.py`) appends one line per event to `subagents.jsonl`, and only inside Orca (it needs `$ORCA_TERMINAL_HANDLE`, which ties the line to the session whose terminal ran it):

```json
{"v": 1, "event": "start", "at": "2026-11-03T12:00:00Z", "agent": "<agent_id>", "claude_session": "<parent session_id>",
 "type": "Explore", "handle": "<terminal handle>", "cwd": "<cwd>", "desc": "<the Agent call's description>"}
```

`agent`, `type`, `claude_session` and `cwd` come from the hook's documented input fields (`agent_id`, `agent_type`, `session_id`, `cwd`). `desc` does not: it comes from the `agent-<id>.meta.json` Claude Code keeps beside the subagent's transcript, and is null when that file or its `description` is missing. A field the event lacks is null; an event with no usable `agent_id` writes nothing. `fleet.subagents()` is the only reader: it folds the lines per agent (a start sets `started_at` and clears `stopped_at`, a stop sets `stopped_at`) and skips any line that is not a well-formed version 1 row; a log it cannot read gives the last fold it read. Each collect puts the agents with no stop on the session holding their terminal, as `subagents: [{agent, type, desc, started_at, stale}]`, newest first and at most 20 per session. The collector remembers that session, so an agent stays on it, as stale, after its terminals close; the link is dropped once the agent stops. An agent never seen under a listed terminal is left out rather than guessed onto another session in the same folder.

Writers take `subagents.jsonl.lock`. A hook that cannot get it within a second drops its event rather than wait. A writer ends a line an earlier one left half-written before adding its own, so that line is skipped alone. Past 1 MiB the log is copied to `.1`, then rewritten with only the starts of the last 7 days that have no stop; if either step fails, the log stays as it was.

Hooks of one event run in parallel, so the logger cannot see whether `claim_check.py` blocked the same stop. It runs claim_check's own judge and writes no stop for a stop claim_check blocks, since the subagent goes on working. A stop another plugin blocks is still written. Whether resuming an agent fires a new `SubagentStart` is not verified; until one arrives, a resumed agent reads as ended. The hook prints nothing and exits 0 on any error, a failed write included, and after 3 seconds whatever it is doing, so it holds up a subagent at most that long. It is loaded when a session starts: a session already running needs `/reload-plugins` or a restart first.

### Adoption into Orca's parent field

The tree above is computed; Orca's `parentWorktreeId` is left alone by default. `orch-dash adopt` prints the parent each session would get. `orch-dash adopt --apply` writes it with `orca worktree set --parent-worktree`, only for sessions that have no parent yet, only when the config sets `adopt.write_orca_parent` to true, and logs each write with the previous value to `adoption.jsonl`. `orch-dash adopt --undo all` (or `--undo <worktree id>`) restores the logged values.

| `requests.jsonl` | Left by the removed owner-request ledger; nothing reads or writes it |
| `stages.json`, `stages-auto.json` | The stage table: what `orch stage` recorded, and the rows each tick generates per program ([stage-table.md](stage-table.md)) |
| `jobs.json` | Each orch-dash job's last run (jobs inside an automation, above) |
| `sends.jsonl`, `adoption.jsonl` | Refused or failed send attempts, prompt answers and opens; adoption writes and undos. A typed line is in `sent/`, and the file before that move is `sends.archive.jsonl` (read-only) |
| `prompts/` | The latest permission request per terminal, from `hooks/permission.py`; dropped after 2 hours or once answered; hidden while Orca does not list its terminal (a record under 5 minutes old is shown anyway) |
| `subagents.jsonl`, `.1`, `.lock` | Each subagent start and stop `hooks/subagent_log.py` observed (Subagents, above); past 1 MiB the file is copied to `.1` and keeps only its open starts of the last 7 days |
| `avatars/` | Reviewer avatars |

The optional config is `$ORCH_FLEET_CONFIG` or `~/.config/agent-skills/dashboard/config.json`:

```json
{"root_worktree": "<orca worktree id>", "adopt": {"write_orca_parent": false},
 "include_main_worktrees": false, "bots_in_inbox": false, "reload_alert_tries": 3, "board": {"stage_warn_h": 6},
 "orca_environment": "<the name another device saved for this host's Orca server>"}
```

`orca_environment` turns the Orca button's copy into a switch command for that device (The Orca button, above); unset, the copy is where the session is.

`board` holds the brief renderer's limits (`state_min`, `done_fold_h`, `stage_idle_d`, `subagent_stale_h`, … in `scripts/board.py` `LIMITS`; the collector reads `subagent_stale_h` too) and `stage_warn_h`, the hours after which the reorient hook says a program's generated stage rows are stale (default 6).

Everything collected passes through one masking step before it is written or shown: GitHub, Slack, Anthropic, OpenAI and AWS token shapes, JWTs, `Authorization`/`Bearer` values, and `*_TOKEN`, `*_SECRET`, `*_PASSWORD`, `*_API_KEY`, `*_CUSTOM_HEADERS` assignments. No credential is read or stored: `gh` uses its own login. `ORCH_FLEET=off` turns the fleet collector off; `orch-dash demo` and the tests point `ORCH_FLEET_STATE` at a temporary directory and replay an invented machine.

```sh
orch-dash fleet                          # one collect, prints a summary
orch-dash inbox add --type login --title "Log in to the registry" [--session <worktree id>] [--url URL] [--command CMD] [--key KEY]
orch-dash inbox resolve --key KEY
orch-dash inbox list                     # added items not resolved, oldest first
orch-dash adopt [--apply] [--undo all|<worktree id>]
```

## Skill usage

`scripts/skill_usage.py` (`orch-dash skills`) reads the local Claude Code transcripts (`$CLAUDE_PROJECTS_DIR` or `~/.claude/projects`, subagent transcripts included) and the installed skills: this checkout's `skills/`, each plugin in `~/.claude/plugins/installed_plugins.json`, and `~/.claude/skills`. `serve` runs it when `<fleet state>/skills.json` is missing or 15 minutes old; the page reads `/api/fleet/skills`. `ORCH_SKILLS=off` turns it off. The signals ledger (`_skill-usage/ledger.jsonl`) holds the signals; `skills.json` stores only what it counts back from that file at collect time (`signals.week` for the ISO week and `signals.rows` in all), never a count of its own.

| Trigger | Counted from |
|---|---|
| auto | a `Skill` tool call |
| chained | a `Skill` tool call whose `attributionSkill` is another skill loaded earlier in the same turn |
| slash | a human message carrying `<command-name>/<skill></command-name>`; a built-in command that is not a skill is dropped |

A **miss** is a human prompt (not a subagent's, a slash command, a notification, a compaction summary or an interruption marker; text inside a `<pasted_content>` block is ignored) that contains, as whole words, a quoted trigger phrase from a skill's description, with no invocation of that skill before the next human prompt. A phrase counts when it has two or more words, or four or more non-ASCII characters; phrases in a sentence starting with "Not", "Never" or "Don't" are skipped. It is a heuristic: read the number as "look here", not as proof. A subagent's prompt matched the same way counts in `subagent_misses_30d` instead: the model that delegated wrote it, so it raises no flag, and `skill_usage.py misses <skill>` marks those rows `(subagent)`.

`denominators` counts, for the last 7 and 30 days, the moments `explain-code` (how and why modes) and `fan-out` compete could have run, to read their use counts against: `explore_calls` (an `Agent` call with `subagent_type` `Explore`), `git_history_cmds` (each `git blame`, or `git log` with `-S`, `-G` or `-L`, run in a `Bash` command; git only named inside a string does not count), and `architect_sessions` (this plugin's `architect`) with how many of them also ran `fan-out` compete, seen as a `Read` of `fan-out/references/compete.md` since the `Skill` call does not name the mode, or called `arena` before it merged into `fan-out` (`architect_sessions_with_arena`). The command line prints the 7-day figures.

| Flag | When |
|---|---|
| `unused_30d` | An installed skill with no use in 30 days. Shown here only: zero uses alone is not a signal |
| `retire_candidate` | No use for three 30-day windows, counted from its last use or from when the collector first saw it (both kept in the cache, so a deleted transcript does not age a skill), with misses or another skill quoting the same trigger phrase (`overlaps`) as evidence, and not rare by design: `RARE` in `skill_usage.py`, plus `rare` in `~/.config/agent-skills/skill-usage.json` for the user's own skills |
| `slash_only` | Used in 30 days, but only ever typed as `/name`: the description does not make it fire. A skill with `disable-model-invocation` set to true (`slash_by_design`) is never flagged: only a human can call it |
| `misses` | More than 3 misses in 30 days (`--misses N`), and at least a fifth of the prompts that carried its phrases (misses plus auto and chained uses): a skill that fires on most of them is not flagged for the rest |

Per skill, the report also keeps what a miss needs to be checked: the matched phrases with their counts (`miss_phrases`, top 3, text from the skill's own description), how many sessions they came from and the last one's time. `skill_usage.py misses <skill>` lists each miss in 30 days with its time, session id and phrase, and `claude --resume <session>` opens one. The page shows the count and top phrase on the chip and the rest on hover, and hides flags on sources this machine cannot edit unless *Flags on all sources* is picked. No prompt or message text is copied, repositories are counted, not named, and the incremental cache (`skill-usage-cache.json`, keyed by a hash of each transcript's path, checked by size and mtime) stores working directories as hashes. The first scan reads every transcript; later ones re-read only changed files.

### Signals for the improvement loop

Each collect appends one row per flag other than `unused_30d`, per skill, per ISO week to `$PROGRAMS_HOME/_skill-usage/ledger.jsonl`, only for sources the loop can edit (`agent-skills` and `user`). The row has the shape of a program ledger's `signal` row, with `kind` `skill_usage`:

```json
{"ts": "2026-09-27T14:51:28Z", "ev": "signal", "kind": "skill_usage", "skill": "agent-skills:swarm",
 "source": "agent-skills", "flag": "retire_candidate", "suggest": ["merge", "retire"],
 "evidence": "skill-usage:agent-skills:swarm:retire_candidate@2026-W39",
 "note": "retire_candidate; suggest: merge|retire; 0 uses in 30 days (0 auto, 0 slash, 0 chained), 0 misses, last used never; basis: overlaps agent-skills:arena; unused since first seen 2026-06-20T09:00:00Z"}
```

`evidence` (skill, flag and the ISO-week window) is the idempotency key, so a flag that persists shows up once a week. The collector writes only this file. The flow improver reads it as one input, and `reflect` promotes a signal into the lessons ledger (Source `skill-usage`, Kind `usage`, Evidence a pointer to the row and its window, one row per skill and flag whose Occurrences rise per window); no script writes the lessons ledger. `suggest` lists what may be proposed; retiring a skill is only ever proposed, never applied by the loop.

## PR stats

`scripts/pr_stats.py` (`orch-dash prstats`) searches GitHub with `gh api graphql` for every pull request created since `since`, one search per source per month (a month at the 1,000-hit search cap is split in halves until each part fits), and writes counts to `<fleet state>/pr-stats.json`. `serve` runs it when the file is missing or 6 hours old, and an hour after a failed collect, which keeps the last counts and adds the error the page shows above them. `serve`'s collect also fails when a source lost more than a quarter of its PRs since the last report with the same `since` and sources, since search leaves out what the token cannot reach (an organization whose SAML SSO blocks it, a GitHub App installed on fewer repositories) without any error; the message names the source. `orch-dash prstats` by hand saves such a drop.

Every search runs once per ghtkn app (`ghtkn exec -e GH_TOKEN -- gh api graphql`, `GHTKN_APP` set for that child only) and the hits are united by URL, because no one app reaches everything: an organization app misses personal repositories and the personal app misses the organization. `pr_stats.apps` lists the apps (unset or `[]` searches under gh's own login as before). An app that gets no token (agent locked, app not authorized) fails the collect with its name; it never falls back to gh's login, which would drop the organization silently. A search costs one call per app, so a collect takes as many times longer as there are apps. The page reads `/api/fleet/stats`. `ORCH_PR_STATS=off` turns it off.

The first source is always the PRs I authored (`author:@me`). Agents that open PRs on my behalf are added under `pr_stats` in the fleet config:

```json
{"pr_stats": {"since": "2025-01-01", "apps": ["acme/write", "me/personal"], "sources": [
  {"name": "Devin", "query": "author:devin-ai-integration[bot] involves:@me"},
  {"name": "Claude", "query": "in:body \"Requested by Your Name\"", "author": "claude"}]}}
```

`query` is GitHub search syntax added to `is:pr archived:false`; `author` keeps only hits whose PR author has that login, for a body line other bots also write. Search cannot OR qualifiers such as `author:` and `in:body`, so each source is its own search. A PR several sources find counts once, for the first. An agent whose commits carry my name is told apart only by what its PR shows (its author login or a line in the body), and `involves:@me` also matches agent PRs I only reviewed. `since` defaults to January 1 of last year.

Days, weeks (from Monday) and hours are in the server's time zone. A trend line is a least-squares fit without the last month or week, which is still filling. A campaign is one title on 10 or more PRs (`BATCH_MIN`); the "Without campaigns" view drops them. The file holds counts, repository names and campaign titles, no PR text.

The Monthly, By source and Weekly charts show 90 days, 6 months (the default), 12 months or everything, and their y-axis fits the range shown, so early months of a handful of PRs do not flatten to zero under recent months of hundreds. The trend line stays the fit over the whole history. The KPIs above them always count the whole history. Pointing at a bar shows one tooltip for its month or week: each series, the total, and the trend and 4-week average there. There is no log scale: on stacked bars it would misstate each segment's share.

## Freshness

The bar under the headline shows each source's last success, both as a local time and as a relative time that ticks every second.

| Source | Warn after | Stale after |
|---|---|---|
| Ledger, Orca | 60 s | 180 s |
| Tracker, GitHub | 3 × `github_every_s` | 6 × `github_every_s` |

When a source is stale, the panels built from it are greyed out. Treat a grey panel as possibly wrong, not as current. A closed or quiet program's unpolled sources are not greyed out.

Every table sorts by a column when its head is clicked. A relative-time column sorts by how long ago, so ascending is newest first. The second click reverses, the third returns to the view's own order, and the browser remembers the choice.

## Panels

- **Headline.** The Orca run objective, with one segment per predicate ticket underneath.
- **Overview**
  - The `next` line mirrors `orch status` step 4, for example "may spawn 1 more" or "SAFETY STOP: main is red".
  - KPI tiles: predicate done (with what the last open item waits on, and the current scope: predicate items plus admitted follow-ups, done out of total, and how many untriaged follow-ups may still join; a count, not a percentage, because the scope can grow), main (with the commit and, when the ledger note names one, its CI run), in-flight/cap with free slots, oldest open PR, PRs awaiting landing, landed in 24 h; human wait only under human-gate.
  - **Now.** Every in-flight worker and what its session is doing, from the tail of its transcript: a tool call (with its description or command), thinking, a finished turn waiting for input, or waiting for a wake-up it armed itself (ScheduleWakeup, Monitor, a background command). A pulse marks the ones moving; a row flashes once when its state changes. Workers without a matching transcript show only the available host activity.
  - **Stages.** Each top-level issue of the tracker project that has children, with its leaf tickets done (green) and in progress (moving stripes). Linear's list carries no parent links, so the tree is crawled with `tracker.py children` a few nodes per collect and cached in `tree.json`: a new program shows "counting N" for a few minutes. Canceled leaves are left out.
  - **Land order**, from `prog.land_order`, shown only while a PR waits to land or a base's exclusive lane is held. Each row shows:
    - position, PR and ticket
    - an age badge (amber over 2 h, red over 3 h)
    - a state chip: ready, catching up, blocked or waiting
    - the first reason it is not moving
  - **Landing.** Who holds each base's lock, from `lock_acquired`/`lock_released`. If there are no lock events, it reads "no one landing".
  - **Needs attention.** A red main, PRs waiting on the human gate, a worker on a permission prompt, stalled workers (turn ended 15+ min with its task open, nothing written 10+ min after dispatch, one tool call over 45 min, nothing written 20+ min after input such as a task-notification that never started a turn), free slots with ready tasks (only when `next` says "may spawn"), landed cards still open, ledger gaps (running dispatches never recorded, merged PRs the ledger never saw, landings without a main CI result; a failed GitHub compare is not asked again for 5 minutes, and never while core quota is under 500; a landing without an answer yet is left out of the gaps. A warm-up before the program lock asks at most 40 new compares per collect, a program's optional `repo_dir` (a local clone) answers with `git merge-base --is-ancestor` at no cost, answers are kept in `<store>/.compare-cache.json` across restarts, and a landing older than 14 days is not reported), untriaged open follow-ups, the latest risk note, and source errors. `orch status` prints the same stalls, slots and gaps.
  - Burn-up, predicate progress and recent activity. The in-flight chart is under Workers and the derived-vs-done chart under Issues. The charts run from the program's `created_at`, or from 30 days back in a longer program; each line starts at the left edge with the values then in force. The in-flight chart starts at the first live Orca sample: backfilled rows carry none.
- **Issues.** Tracker issues the program touched, with state, class and PR.
- **PRs.** Open and recent PRs, showing:
  - CI. Closed and merged PRs come without checks and reviews (with them, a 200-PR window timed out); they keep what a collect saw while they were open, or read "not fetched"
  - the review verdict against the current head
  - review rounds
  - merge state
  - the PR's position in the land order
- **Tasks.** The Orca task DAG, with `dep` ledger edges added.
  - Node colours show status: done, landing, blocked, in progress, waiting.
  - The critical path is the longest unfinished chain.
  - On narrow screens the DAG becomes a list.
- **Workers.** Orca workers, showing:
  - stage, liveness and model
  - worktree
  - tokens (Claude only)
- **Activity.** Ledger events and notes, newest first. This includes `dep`, `land_check`, `lock_*`, `yield` and `reprioritized`.

### Tokens

Tokens are read from Claude Code transcripts in `~/.claude/projects/<worktree path>/*.jsonl`. Rows are deduplicated by `message.id`, and each run reads only the bytes appended since the last one.

Workers without measured usage show `n/a`. Subagent transcripts in subdirectories are not counted.

## Notes

A note is a short line of human or model judgement that the collectors can't compute. The newest risk note also appears under Needs attention.

```sh
orch-dash note <slug> --kind risk|digest|decision --text "..." [--author name]
```

Notes are appended to `notes.jsonl`, capped at 500 characters, and appear from the next collect, which happens within 3 s while `serve` runs. Use them for:

- **risk:** something the numbers don't show, for example "ACME-107 copy still unapproved".
- **digest:** a one-line summary of the last hour.
- **decision:** a call you made and why.

## Optional: a cheap annotator

The dashboard is complete without one. If you want a periodic digest, schedule a small agent. It should read only `state.json` and write at most three notes:

```sh
orca automations create --name "dash notes: <slug>" --trigger "*/15 * * * *" --provider claude \
  --extra-agent-args="--model haiku" --workspace <selector> --workspace-mode existing \
  --prompt "Read \$PROGRAMS_HOME/<slug>/dashboard/state.json only. If something needs a human (stalled land order, idle worker, stale source, main red), write at most 3 lines with: orch-dash note <slug> --kind risk|digest --text '...' --author annotator. Otherwise write nothing."
```

Before you run this, check `orca automations create --help`. Flags vary by Orca version.

Alternatively, a Haiku worker that the lead spawns on the same prompt does the job. Each run costs a few thousand tokens, mostly for reading `state.json`. Leave the annotator off unless someone reads the notes.
